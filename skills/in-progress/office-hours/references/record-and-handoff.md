# Record, review and close

Read after the user selects an approach, or when resuming a selected direction. This is a product decision record; screens and technical specifications belong to their own roles.

## Record the choice

Call the Skill tool with "product-brief" to create or update the canonical brief. Supply the user's choice, evidence, mode, agreed/unresolved premises and exact source locators. Without a Skill tool, read the installed product-brief instructions; if absent, write the same bounded decision record and report the missing capability. Reuse the project convention, and save one record in the authorized workspace. For a conversation-only task, show the record inline rather than writing unsolicited files.

Include the relevant parts: problem/opportunity, current alternative, startup evidence or builder delight, target situation, constraints, premises, approaches and choice, reasons, open questions, success observations, dependencies, and next action. Retain rejected directions in one line each. Distinguish user decisions, proposals and unknown facts. An absent distribution or implementation choice stays open rather than forcing an architecture.

Keep one decision plus its reason per bullet. Preserve explicit supersession if replacing an old record. A PRD can be the canonical brief; avoid a second independently maintained truth. A session-specific reflection may quote a concrete insight or change in framing, without inventing a personality profile.

## Bounded document review

Before final presentation, check completeness for the selected next task, consistency, clarity, scope and known feasibility. When the host permits an independent reviewer, use fresh context with the record and evidence, not the whole coaching history. Cap at three rounds or the user's smaller limit. Re-review changed blockers only; stop on no blocking issues, unchanged persisting blockers, failure, or the cap. Carry every unresolved material concern to the user.

Preserve original findings and evidence. An attempted correction is not independently verified until a reviewer checks it. Missing or failed review is explicitly unreviewed; it does not block presenting the record. Without delegation, label a self-check as a self-check. No invented quality score or cross-model claim.

## Approval and closing

Read the final record and reproduce its full body verbatim in the conversation, with a file link if saved. Use that text as the visible record rather than composing a second summary. Ask whether the user approves, wants a scoped revision, or wants to revisit the direction; wait. Reuse approval already supplied for unchanged decisions and ask only about newly proposed choices. A draft recommendation is not approval.

Close with one concrete action. Startup mode: an observation, customer action or evidence check that changes a decision. Builder mode: what to build or try first, with an observable outcome. If useful, point out one specific insight from this conversation. No promotional or ongoing profile work is implied.

When the next task is included in the user's request, product-brief prepares the appropriate handoff after the approval. Design takes the product contract and selected prototype into structure/flows/screens; engineering takes those and the latest design into technical synthesis. Recommend human invocation of to-spec or to-tickets when appropriate. Prototype evaluation goes to prototype-user-test for fresh AI task attempts or experiment-design for human/AI-quality evidence plans. Neither is a prerequisite for every idea.

Done when the user can see the choice and its reason, remaining concerns and the next action. This skill's output does not itself execute that action or establish product validation.
