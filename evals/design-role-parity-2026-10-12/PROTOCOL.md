The acceptance requirement is [original quality as the minimum](../design-beta/quality-floor.md). This protocol is fixed before execution. Results and repairs are recorded separately. The 2026-10-10 cases remain regression evidence, not hidden evaluation cases.

Each role has three small task families: ordinary use, an edge or stateful use, and preservation or bounded behavior. Each condition gets two fresh role execution contexts, for 68 planned role runs and 204 case executions. Three cases within a role run share a context and fixed ordering but have separate files. Thus cases within one run are not independent samples. Repeats and conditions share neither model context nor output. Additional repairs receive new identifiers and never overwrite failed runs.

This is a representative role suite, not proof over every possible input or a statistical noninferiority test. A branch matrix records which source branches are exercised, omitted or blocked. A role with a required untested branch cannot receive an unqualified full-role acceptance.

## Conditions

Freeze candidate files, fixture files, task, source revision and evaluator criteria before dispatch. Preserve hashes, the invocation prompt, output, tool failures, elapsed time and available telemetry. Use identical model and effort settings, tools, permissions, time limits, scenario data, locale and viewport in paired conditions. Unknown telemetry stays unknown. Explicit invocation is tested separately from automatic discovery. Original dependency skills are supplied from the same original bundle; Paul dependencies come from the fixed candidate bundle. No-skill controls get the same task and tool access without the design skill files.

Executor contexts receive the user task, relevant skill folder and input artifacts. They cannot read the evaluator rubric, other conditions, prior findings, repository skill source or hidden reference implementation. Context isolation is enforced by setup and instructions; filesystem isolation limitations are disclosed. Executions use disposable copies. Review tasks preserve all source bytes. Implementation and exploration tasks change only permitted local files. No production writes, public messages, purchases, installation, publishing or promotion are part of these trials.

Use Playwright CLI for implementation observations and QA, Aside for research where applicable. Explicit user tool choices take precedence. Local source-only tasks require no browser. Record missing tool integrations as unavailable; static analysis cannot substitute for a claimed runtime observation. Each executor owns its session and closes only that session.

## Evaluator criteria

Before seeing outputs, record expected required behaviors and important failure cases in an evaluator-only rubric. These examples are not an exhaustive truth set. Independently verify new findings, equivalent solutions and disputed omissions. Score semantic outcomes and task impact rather than matching phrases, report length or raw finding counts. The original can be wrong; its verified mistake is not a target.

Acceptance requires required artifacts and behavior, preserved valid original capabilities, correct evidence and no unresolved new regression. A critical original finding missed by Paul blocks the role. Supported lower-severity omissions also require reconciliation rather than offset by extra findings. Cosmetic improvements cannot offset broken behavior, fabricated observations, scope violations or accessibility regressions. A clean case tests unnecessary intervention and false positives, not compliance with an instruction to report zero findings.

For rendered outputs, replay relevant keyboard, state, responsive and recovery behavior. Align screenshot conditions before visual comparison. Screenshots alone do not demonstrate motion quality, real assistive technology, touch behavior or performance. Human A/B review is required for subjective visual acceptance. Produce reviewable pairs before requesting that input.

## Repair and composition

Repair the smallest responsible instruction only after observing a failure. Preserve provenance revisions, update the local digest and record the reason. Re-run the failing case and a new independent task; when shared dependencies change, identify and rerun affected roles before applying their old results to the new version. Repeated tuning on an exposed case is development, not hidden validation.

After independent roles, run PM brief to IA to user-flow to wireframe to implementation to review. Check stable object, screen and state identifiers, requirement traceability, recovery paths, responsive priorities and evidence handoffs. Test invocation boundaries separately: the five explicit-only skills remain human choices. A composition pass does not upgrade a missing independent role pass.

Publish one row per role with source/candidate identity, cases and repeats completed, observations, verified regressions, branch gaps and bounded decision. Keep product defects in review fixtures distinct from failures of the reviewer skill. Keep quality acceptance distinct from plugin validation and explicit promotion approval. All 17 candidates stay in-progress until the user validates the behavior and explicitly approves promotion.
