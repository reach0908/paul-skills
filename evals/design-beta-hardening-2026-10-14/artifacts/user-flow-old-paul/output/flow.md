# T-SAVE 사용자 흐름 계약

## 1. 근거와 범위

- 근거 문서: `TASK.md`, `BRIEF.md`의 **PB-72 revision 3**
- 흐름 ID: `T-SAVE`
- 행위자: 팀 읽기 목록의 자료를 읽고 자신의 보관함에 저장하려는 사용자
- 진입 위치: `D-ITEM` (`/items/R-72`), 자료 `R-72` — **작은 팀에서 실패 후 다시 시도하기**
- 진입 문맥: `D-LIB`에서 검색어 `q='작은 팀'`, 태그 `운영`, 정렬 `newest`, 목록 위치 `R-72`를 가지고 상세에 진입한 상태
- 의도한 결과: 작성 중인 메모와 `R-72`의 저장 작업이 서버에서 성공으로 확정된다.
- 관찰 가능한 성공: 서버의 `succeeded` 결과와 유일한 receipt `S-72`를 함께 받은 상태다. `pending`, 타임아웃, 화면 닫기만으로는 성공으로 보지 않는다.

이번 문서는 T-SAVE의 작업 상태와 전이만 정한다. 화면 배치, 화면 코드, 상태 전시용 페이지, API 스키마, 새 전역 메뉴는 범위 밖이다. 저장 완료 후 자동으로 `D-SAVED` (`/saved`)로 이동하는 동작도 입력 문서에 없으므로 정하지 않는다.

## 2. 확정 사실과 계약 표기

### 입력에서 확정된 정책

- 최초 저장 요청은 `pending` 표시 후 `timeout-unknown`이 된다. 이는 성공도 실제 실패도 아니다.
- `timeout-unknown`의 승인된 복구는 **같은 작업의 상태 확인**이다. 새 저장 요청 재전송이 아니다.
- 상태 확인 1회차 결과는 `pending`, 2회차 결과는 `succeeded`이며 receipt는 `S-72`다.
- 닫기는 서버 작업을 취소하지 않는다. 메모 초안은 유지한다.
- 같은 요청의 중복 저장 입력은 무시한다.
- 인증 복구 후 같은 키로 작업을 다시 조회하는 서버 API는 미정이다.
- 기존 뒤로가기 문맥(`q`, `tag`, 정렬, 목록 위치)은 유지한다.

### 상태 계약을 위한 표기

- `K`는 같은 저장 작업을 식별하는 **불투명한 요청 키**를 뜻한다. 키의 실제 이름, 형식, 발급 주체는 정하지 않는다.
- 작업 상태(`S-*`)와 보기 노출 상태(`V-*`)를 분리한다. 따라서 화면을 닫아도 서버 작업 상태는 유지되거나 서버 응답에 따라 진행될 수 있다.
- 닫기 후 어느 셸/경로가 보이는지는 입력 문서에 없다. `V-CLOSED`는 오직 T-SAVE 보기가 보이지 않는다는 뜻이며, 새 목적지를 발명하지 않는다. 기존 뒤로가기를 사용한 경우에만 위의 `D-LIB` 문맥 보존 규칙을 적용한다.

## 3. 작업 상태 표

| 상태 ID | 의미 | 사용자가 알아야 할 정보 | 이 상태에서 가능한 T-SAVE 행동 | 보존 데이터 |
|---|---|---|---|---|
| `S-SAVE-00-DRAFT` | 요청 생성 전, 메모 초안 작성 상태 | 아직 저장 요청이 없고 성공도 아니다. | 초안 변경, 저장 시작, 닫기 | 메모 초안, `R-72`, 진입 문맥. `K`와 receipt는 없음 |
| `S-SAVE-10-REQUESTING` | 최초 저장 요청 진행 중 | `pending`; 완료 여부 미확정 | 닫기. 같은 요청의 중복 저장 입력은 무시 | 초안, `R-72`, `K`, 진입 문맥 |
| `S-SAVE-20-TIMEOUT-UNKNOWN` | 최초 요청이 타임아웃되어 서버 처리 여부를 모름 | **알 수 없음**이며 실패/성공으로 단정하지 않음 | 같은 `K`로 상태 확인 1회차, 닫기. 저장 재전송은 금지 | 초안, `R-72`, `K`, `check_count=0`, 진입 문맥 |
| `S-SAVE-30-CHECKING-1` | 상태 확인 1회차 진행 중 | 저장 재요청이 아니라 조회 중 | 닫기. 같은 저장 입력은 무시 | 초안, `R-72`, 같은 `K`, `check_count=1`, 진입 문맥 |
| `S-SAVE-40-SERVER-PENDING` | 상태 확인 1회차에서 서버 `pending` 확인 | 아직 완료되지 않았고 실패도 아님 | 같은 `K`로 상태 확인 2회차, 닫기. 저장 재전송은 금지 | 초안, `R-72`, 같은 `K`, `check_count=1`, 진입 문맥 |
| `S-SAVE-50-CHECKING-2` | 상태 확인 2회차 진행 중 | 저장 재요청이 아니라 조회 중 | 닫기. 같은 저장 입력은 무시 | 초안, `R-72`, 같은 `K`, `check_count=2`, 진입 문맥 |
| `S-SAVE-60-SUCCEEDED` | 서버가 저장 성공을 확정 | 성공과 receipt `S-72`를 함께 식별 가능 | 닫기. 같은 요청의 중복 저장 입력은 무시 | 초안, `R-72`, 같은 `K`, `result=succeeded`, `receipt=S-72`, 진입 문맥 |
| `S-SAVE-70-FAILED` | 서버가 **명시적이고 종결적인 실패**를 반환 | 실제 실패임을 표시하며 timeout-unknown과 구분 | 닫기. 같은 요청의 중복 저장 입력은 무시. 새 시도 정책은 미정 | 초안, `R-72`, 같은 `K`, `result=failed`, 실패 정보, receipt 없음, 진입 문맥 |
| `S-SAVE-80-AUTH-REQUIRED` | 상태 확인이 인증 요구로 중단 | 저장 결과는 여전히 미확정이며 새 저장을 보내면 안 됨 | 기존 인증 복구로 이동하거나 닫기 | 초안, `R-72`, 같은 `K`, 직전 확인 단계, 진입 문맥 |
| `S-SAVE-81-REQUERY-UNRESOLVED` | 인증은 복구됐지만 같은 `K`의 재조회 방법이 미정 | 인증 성공이 저장 성공을 뜻하지 않음 | 닫기. 후속 상태 확인은 서버 API 결정 전까지 진행 불가 | 초안, `R-72`, 같은 `K`, 직전 확인 단계, 진입 문맥 |

`S-SAVE-70-FAILED`는 실제 실패의 의미를 분리하기 위한 계약 상태다. PB-72의 고정 검증 경로는 `timeout-unknown → pending → succeeded(S-72)`이므로 이 실패 분기를 실제로 발생시키지는 않는다.

## 4. 보기 노출 상태 표

| 상태 ID | 의미 | 작업 상태와의 관계 |
|---|---|---|
| `V-OPEN` | T-SAVE 보기가 열려 있음 | 현재 `S-*` 상태에 맞는 피드백과 허용 행동을 노출 |
| `V-CLOSED` | T-SAVE 보기가 닫혀 있음 | 현재 `S-*` 상태와 서버 작업을 취소하지 않음. 초안, `K`, 결과, receipt를 해당 상태에 맞게 유지 |

모든 `S-*` 상태는 `V-OPEN` 또는 `V-CLOSED`와 조합될 수 있다. 닫힌 동안 이미 시작된 요청/상태 확인의 응답이 도착하면 해당 시스템 전이는 그대로 적용되고, 재진입 시 최신 작업 상태를 보여 준다. 응답을 받지 못했다면 닫기 전의 마지막 확인 상태를 복원한다.

| `TR-SAVE-13` | 모든 `S-*` + `V-CLOSED` | `R-72`의 T-SAVE 보기에 재진입 | 동일 사용자/저장 작업을 복원할 수 있음 | 닫힌 동안 수신된 응답을 포함한 최신 작업 상태 표시 | 현재 `S-*` + `V-OPEN` | 요청 전이면 `K`/receipt 없음. 진행 중이면 같은 `K`, 완료 후면 `S-72`, 실패면 실패 정보를 복원 |

`TR-SAVE-09`는 실제 실패를 정의하는 대체 분기다. PB-72의 지정 응답(`TR-SAVE-04`, `06`, `08`)과 동시에 적용하지 않는다. 단순 타임아웃은 이 전이의 전제 조건을 만족하지 않는다.

## 6. 경로 점검

| 경로 ID | 점검 경로 | 결과 |
|---|---|---|
| `PATH-SAVE-01` | `S-SAVE-00-DRAFT`에서 저장 → `S-SAVE-10-REQUESTING` → `S-SAVE-20-TIMEOUT-UNKNOWN` → 1회차 확인 `S-SAVE-30-CHECKING-1` → `S-SAVE-40-SERVER-PENDING` → 2회차 확인 `S-SAVE-50-CHECKING-2` → `S-SAVE-60-SUCCEEDED`/`S-72` | **일관됨.** 성공은 마지막 서버 확인에서만 성립하고 중간 상태는 성공/실패로 오인되지 않음 |
| `PATH-SAVE-02` | `S-SAVE-00-DRAFT`에서 초안 작성 → 닫기 → 재진입 | **일관됨.** 초안은 복원되며 아직 요청 전이므로 `K`와 receipt는 없어야 함 |
| `PATH-SAVE-03` | `S-SAVE-30-CHECKING-1`에서 닫기 → 닫힌 동안 1회차 pending 도착 → `S-SAVE-40-SERVER-PENDING`으로 재진입 → 2회차 확인 계속 | **일관됨.** 보기 닫기와 서버 작업 상태가 분리되고 같은 `K`가 유지됨 |
| `PATH-SAVE-04` | 요청 키가 있는 상태에서 같은 저장 입력 반복 | **일관됨.** `TR-SAVE-03`으로 흡수되며 새 저장 요청이나 새 `K`가 생기지 않음 |
| `PATH-SAVE-05` | 조회 중 명시적 종결 실패 응답 → `S-SAVE-70-FAILED` | **의미 구분은 일관됨.** 초안/`K`는 남고 receipt는 없으며 실제 실패로 표시됨. 다만 PB-72의 고정 응답 경로에서는 발생하지 않아 실행 검증되지 않음 |
| `PATH-SAVE-06` | 조회 중 인증 요구 → `S-SAVE-80-AUTH-REQUIRED` → 인증 성공 → `S-SAVE-81-REQUERY-UNRESOLVED` | **의도적으로 미완결.** 같은 `K`를 새 저장으로 재전송하지 않으며, 인증 후 재조회 API 결정 전에는 성공/실패로 진행하지 않음 |
| `PATH-SAVE-07` | `S-SAVE-60-SUCCEEDED` 성공 후 닫기 → 재진입 | **일관됨.** 성공 결과와 receipt `S-72`, 초안이 유지됨 |

표에 제시된 사용자 행동은 모두 전이와 연결된다. 고아 상태는 없지만 `S-SAVE-81-REQUERY-UNRESOLVED`는 아래의 명시적 서버 의존성 때문에 종결되지 않는 상태다.

## 7. 화면이 노출해야 하는 정보와 행동

배치는 정하지 않고, 추후 와이어프레임이 추적해야 할 항목만 적는다.

- `D-ITEM /items/R-72`: 자료 식별 정보, 메모 초안, 현재 작업 상태, 상태에 맞는 저장 또는 상태 확인 행동, 닫기 행동
- `timeout-unknown`: “실패”가 아니라 처리 여부를 모른다는 설명과, 새 저장이 아닌 상태 확인 행동
- 서버 `pending`: 아직 완료되지 않았다는 설명과 2회차 상태 확인 행동
- 성공: `succeeded`와 receipt `S-72`
- 실제 실패: 종결 실패라는 설명. timeout-unknown과 다른 문구/상태명
- 인증 요구/복구 후: 저장 결과가 미확정이며 같은 작업을 이어야 한다는 설명. 새 저장 행동을 복구 수단으로 노출하지 않음
- 닫기/재진입: 초안과 상태 복원. 요청 전에는 존재하지 않는 `K`나 receipt를 표시하지 않음

기존 `출처로 이동`, `본문으로 건너뛰기`, 뒤로가기 문맥은 T-SAVE 데이터를 바꾸지 않는다. 이 문서는 그 기존 동작의 화면 구성을 다시 설계하지 않는다.

## 8. 미결정 사항과 한계

1. **인증 복구 후 재조회 API**: 같은 `K`를 어느 서버 API로, 어떤 인증 문맥에서 다시 조회할지 미정이다. 결정 전에는 `S-SAVE-81-REQUERY-UNRESOLVED` 이후 전이를 구현 계약으로 확정할 수 없다.
2. **실제 실패 후 새 시도 정책**: 새 시도를 허용하는지, 허용한다면 새 `K`가 필요한지와 기존 초안을 어떻게 취급할지 입력에 없다. `S-SAVE-70-FAILED`에서 새 저장으로 가는 전이를 만들지 않았다.
3. **초안 유효성 규칙**: 빈 메모 허용 여부나 길이 제한이 제시되지 않았다. `TR-SAVE-02`에 임의 검증 조건을 추가하지 않았다.
4. **닫기의 시각적 목적지**: 닫기가 어느 경로나 셸을 보여 주는지 제시되지 않았다. 작업 보존 계약만 확정했다. 기존 뒤로가기를 사용하면 `D-LIB` 문맥은 유지해야 한다.
5. **권한/소유권**: 만료된 초대의 팀 자료 읽기 권한과 내 메모/타인 원문의 소유권 정책은 미정이며 T-SAVE에서 확정하지 않았다.
6. **검증 범위**: 이 점검은 제공 문서로 수행한 작성자 수준의 상태 계약 워크스루다. 계정, 라이브 API, 구현 화면, 실제 사용자 테스트를 사용하지 않았으므로 서버 동작과 사용성 성공을 증명하지 않는다.

후속 초안 작성이 가능한 상태이나, 사용자 수용 완료 상태는 아니다. 인증 복구 분기는 1번 의존성이 결정될 때까지 명시적으로 열려 있다.
