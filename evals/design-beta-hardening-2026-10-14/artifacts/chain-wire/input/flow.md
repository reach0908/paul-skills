# T-SAVE 사용자 행동·제품 응답 명세

## 1. 근거와 경계

- **근거:** `BRIEF.md`의 「공유 자료함, 결정본 PB-72 revision 3」, `input/map.md`의 「공유 자료함 정보 구조 맵」
- **행위자:** 팀 읽기 목록에서 자료를 찾아 내 보관함에 저장하는 사용자
- **시작 맥락:** `D-LIB /library`의 검색·필터 결과에서 자료 `R-72`(제목: **작은 팀에서 실패 후 다시 시도하기**)를 선택해 `D-ITEM /items/R-72`에 진입한다. 확정된 복귀 문맥은 `q='작은 팀'`, `tag='운영'`, 정렬 `newest`, 목록 위치 `item R-72`다.
- **의도한 결과:** `R-72`와 사용자가 입력한 내 메모가 내 보관함에 저장된다.
- **관찰 가능한 성공:** 서버가 같은 저장 작업의 상태를 `succeeded`로 확인하고 유일 receipt `S-72`를 반환한다. 그 전에는 성공으로 간주하지 않는다. 성공 후 `D-SAVED /saved`에서 같은 자료 ID `R-72`의 저장 관계와 내 메모를 확인할 수 있다.
- **범위:** 메모 초안 입력, 저장 시작, 비동기 처리, 결과 불명 상태, 상태 확인, 중복 방지, 닫기·다시 열기, 기존 목적지로 이탈·복귀, 성공 후 다음 경로
- **범위 밖:** 화면 배치, 컴포넌트 형태, 정확한 인터페이스 문구, 코드·API 설계, 새 목적지·전역 메뉴, 새 권한 정책

기존 목적지 ID `D-LIB`, `D-ITEM`, `D-SAVED`, `D-HELP`를 그대로 쓴다. `S-72`는 성공 증빙이지 새 목적지가 아니다. 태그와 작성자는 `D-LIB`의 필터이며 목적지가 아니다. 아래 전이 표가 이 문서의 권위 있는 계약이고, 도식은 읽기 보조다.

## 2. 상태 모델과 보존 데이터

### 2.1 두 개의 독립 축

`T-SAVE`의 **작업 상태**와 작업 보기가 열려 있는지는 별개다. 닫기는 `V-OPEN`을 `V-CLOSED`로 바꿀 뿐 작업 상태를 되돌리거나 서버 작업을 취소하지 않는다.

| 축 | ID | 의미 |
|---|---|---|
| 보기 | `V-OPEN` | `D-ITEM`에서 `T-SAVE`의 현재 상태와 가능한 행동을 확인할 수 있음 |
| 보기 | `V-CLOSED` | `T-SAVE` 보기가 닫힘. 작업 상태와 보존 데이터는 남아 있음 |

`V-CLOSED`는 새 목적지가 아니다. 닫기 전후의 라우트나 컴포넌트 형태도 이 명세에서 정하지 않는다.

### 2.2 작업 상태

| ID | 상태명 | 사용자가 알아야 할 의미 | 보유 데이터 | 가능한 핵심 행동 |
|---|---|---|---|---|
| `TS-00` | 시작 전 | 아직 저장 요청이 없음 | `R-72`, 메모 초안, 발견 문맥. 요청 키·receipt 없음 | 초안 입력, 저장 시작, 닫기 |
| `TS-10` | 최초 요청 처리 중 | 같은 저장 요청을 처리 중이며 결과 확인 전 | `R-72`, 메모 초안, 동일 작업 키 `K`, receipt 없음 | 기다리기, 닫기. 반복 저장 입력은 무시 |
| `TS-20` | 결과 불명 | 최초 요청이 시간 초과되어 서버 처리 여부를 모름. 실패도 성공도 아님 | `R-72`, 메모 초안, `K`, 마지막 관찰 `timeout-unknown`, receipt 없음 | **상태 확인**, 닫기. 저장 재전송 금지 |
| `TS-21` | 첫 상태 확인 중 | `K`로 기존 작업의 상태를 조회 중 | `TS-20`의 데이터 | 기다리기, 닫기. 반복 확인·저장 입력은 무시 |
| `TS-30` | 확인된 처리 중 | 첫 상태 확인 결과가 `pending`임 | `R-72`, 메모 초안, `K`, 마지막 확인 `pending`, receipt 없음 | **상태 확인**, 닫기. 저장 재전송 금지 |
| `TS-31` | 두 번째 상태 확인 중 | `K`로 같은 작업의 상태를 다시 조회 중 | `TS-30`의 데이터 | 기다리기, 닫기. 반복 확인·저장 입력은 무시 |
| `TS-40` | 성공 확인 | 서버가 `succeeded`와 유일 receipt `S-72`를 확인함 | `R-72`, 내 메모, `K`, `S-72` | `D-SAVED`에서 확인, 닫기·다시 열기 |
| `TS-90` | 인증 복구 의존 | 인증은 복구해야 하지만, 그 뒤 `K`로 기존 작업을 재조회하는 API가 미정임 | `R-72`, 메모 초안, `K`, 인증 직전 마지막 상태, receipt는 확인되지 않음 | 인증 복구, 닫기. 새 저장 요청은 보내지 않음 |

`K`는 동일 작업을 식별하고 조회·중복 방지에 사용하는 키를 뜻한다. 선행 문서는 실제 키 값, 생성 주체, 형식을 정하지 않았으므로 이 명세도 정하지 않는다. 다만 한 번 생성된 `K`를 `TS-10`부터 성공 확인까지 바꾸거나, 결과 불명 상태에서 새 키로 저장을 재전송해서는 안 된다.

### 2.3 보존 규칙

| 데이터 | 시작 전 닫기 | 처리 중·결과 불명·상태 확인 중 닫기 | 성공 후 닫기 |
|---|---|---|---|
| 자료 ID `R-72` | 유지 | 유지 | 유지 |
| 메모 초안/저장된 내 메모 | 초안 유지 | 초안 유지 | 확인된 내 메모와 저장 관계 유지 |
| 동일 작업 키 `K` | 존재하지 않음 | 유지 | 저장 관계 추적에 유지. 노출 방식은 정하지 않음 |
| receipt | 존재하지 않음 | 확인 전이므로 없음 | 유일 `S-72` 유지 |
| 목록 복귀 문맥 | 유지 | 유지 | 유지 |
| 서버 작업 | 없음 | **취소하지 않음** | 이미 성공한 관계 유지 |

저장 시작 뒤 메모를 추가 편집할 수 있는지, 편집분이 진행 중 요청에 포함되는지는 선행 결정에 없다. 따라서 이 흐름은 `TS-10` 이후의 메모 편집 전이를 제공하지 않으며, 저장을 시작할 때의 메모와 보존되는 초안을 임의로 다르게 해석하지 않는다. 이 정책은 미결 사항 `OD-04`로 넘긴다.

## 3. 핵심 흐름

```text
TS-00 시작 전
  └─ 저장 ─→ TS-10 최초 요청 처리 중
                 └─ timeout ─→ TS-20 결과 불명
                                      └─ 상태 확인 ─→ TS-21 확인 중
                                                           └─ pending ─→ TS-30 확인된 처리 중
                                                                                └─ 상태 확인 ─→ TS-31 확인 중
                                                                                                     └─ succeeded + S-72 ─→ TS-40 성공 확인
```

어느 상태에서든 작업 보기는 닫힐 수 있다. 닫힌 동안 이미 시작된 서버 작업과 이미 시작된 상태 확인의 시스템 결과는 계속 진행하며, 다시 열면 그때의 최신 작업 상태를 보여준다.

선행 결정에는 서버 작업을 취소하는 행동이 없다. 따라서 **닫기와 취소를 같은 행동으로 취급하지 않으며**, 이 흐름에 별도 취소 전이를 새로 만들지 않는다.

| `TR-13` | `TS-10 / V-CLOSED` | 최초 요청이 시간 초과됨 | 닫기 전에 최초 요청이 시작됨 | 보기 밖에서는 별도 화면 반응을 정하지 않음. 다시 열 때 결과 불명과 상태 확인 행동을 제시 | `TS-20 / V-CLOSED` | `TR-03`과 동일 |
| `TR-14` | `TS-21 / V-CLOSED` | 첫 상태 확인이 `pending` 반환 | 닫기 전에 첫 상태 확인이 시작됨 | 다시 열 때 확인된 `pending`을 제시 | `TS-30 / V-CLOSED` | `TR-05`와 동일 |
| `TR-15` | `TS-31 / V-CLOSED` | 두 번째 상태 확인이 `succeeded`와 `S-72` 반환 | 닫기 전에 두 번째 상태 확인이 시작됨 | 다시 열 때 성공과 `S-72`를 제시 | `TS-40 / V-CLOSED` | `TR-07`과 동일 |
| `TR-16` | `TS-20`, `TS-21`, `TS-30`, `TS-31` / `V-OPEN` | 상태 확인 전 또는 도중 인증 복구가 필요해짐 | 기존 `K`가 있으나 인증 없이 조회를 이어갈 수 없음 | 저장을 재전송하지 않고, 인증 복구가 필요하되 복구 뒤 같은 작업 재조회가 미결임을 알림 | `TS-90 / V-OPEN` | `K`, 초안, 인증 직전 마지막 상태 유지. 성공·실패로 변경하지 않음 |
| `TR-17` | `TS-90 / V-OPEN` | 사용자가 인증을 복구함 | 인증 복구 완료 | 후속 API가 정해질 때까지 성공·실패·재시작으로 단정하지 않음 | **미결: `OD-02`** | 같은 `K`와 마지막 상태를 유지. 새 저장 요청 금지 |
| `TR-18` | `TS-40 / V-OPEN` | 사용자가 기존 `D-SAVED` 진입을 선택 | `S-72`로 성공 확인됨 | `D-SAVED`에서 같은 `R-72`와 내 메모를 확인 가능하게 함 | `D-SAVED /saved` | 자료 ID를 바꾸지 않음. `S-72`는 별도 목적지가 아님 |

`TR-03`, `TR-05`, `TR-07`과 `TR-13`~`TR-15`는 각각 보기가 열린 경우와 닫힌 경우의 같은 종류의 서버 사건을 다룬다. 출발 보기별 전이가 분리되어 있어 동일 상태·사건에 두 목적지가 생기지 않는다.

## 5. 이탈·복귀와 목적지 전이

| ID | 출발 | 행동 | 제품 응답과 도착 | T-SAVE 및 문맥 처리 |
|---|---|---|---|---|

| `NAV-02` | `D-ITEM /items/R-72`의 모든 작업 상태 | 기존 뒤로가기 | `D-LIB /library`의 이전 결과와 `R-72` 위치 복원 | 작업 보기는 닫힌 것으로 다룬다. `TS-00`이면 초안만 유지하고 요청은 만들지 않으며, 시작된 작업이면 서버 취소 없이 상태·`K`·초안 유지 |
| `NAV-03` | `NAV-02`로 돌아간 `D-LIB` | 같은 `R-72`를 다시 선택 | `D-ITEM /items/R-72` | `TR-12`에 따라 최신 작업 상태와 초안 복원 |
| `NAV-04` | `D-ITEM /items/R-72`의 모든 작업 상태 | 출처로 이동 | 현재 자료에 연결된 외부 원문 URL | 현재 자료 ID, 작업 상태, 메모 초안을 바꾸지 않음. 돌아오면 같은 `D-ITEM` 문맥 복원. 진행 중 서버 사건은 계속될 수 있음 |
| `NAV-05` | 외부 원문 | 사용자가 원래 상세로 돌아옴 | `D-ITEM /items/R-72` | 외부에 있는 동안 바뀐 서버 상태가 있다면 최신 상태로 제시 |
| `NAV-06` | `D-ITEM /items/R-72`의 모든 작업 상태 | 본문으로 건너뛰기 | 같은 `D-ITEM` 내부의 본문 | 목적지, 자료, 작업 상태, 메모 초안 모두 변경 없음 |
| `NAV-07` | 직접 URL, 추천 또는 `D-SAVED` | `R-72` 상세 진입 | `D-ITEM /items/R-72` | 동일 자료 ID를 쓴다. 선행 문맥별 복귀 목적지·복원 규칙은 `OD-03`으로 유지 |

좁은 화면에서도 기존 `D-LIB`의 검색과 `D-SAVED`는 도달 가능해야 한다. 이는 접근 요구사항이며 특정 메뉴나 화면 배치를 뜻하지 않는다. `D-HELP /help`는 기존 목적지로 유지하지만 `T-SAVE`와의 새 전이는 근거가 없어 추가하지 않는다.

## 6. 상태별 필수 정보와 행동

화면 구성은 정하지 않되, downstream 화면 명세는 아래 정보를 숨기면 안 된다.

| 상태 | 식별 가능해야 하는 정보 | 제공해야 하는 행동 | 제공하면 안 되는 해석·행동 |
|---|---|---|---|
| `TS-00` | 현재 자료 `R-72`, 메모 초안, 아직 요청 전임 | 초안 입력, 저장, 닫기, 기존 목적지 행동 | 요청 전인데 `K`, `pending`, receipt가 있는 것처럼 표시 |
| `TS-10` | 저장 요청 처리 중, 현재 자료 | 닫기 | 반복 입력으로 새 저장 생성 |
| `TS-20` | 결과 불명, 성공·실패가 아님, 기존 작업 `K`를 확인한다는 의미 | 상태 확인, 닫기 | 재시도라는 이름으로 저장 재전송, 실패 또는 성공 단정 |
| `TS-21`, `TS-31` | 기존 작업의 상태 확인 중 | 기다리기, 닫기 | 반복 확인을 병렬 실행, 새 저장 생성 |
| `TS-30` | 상태 확인 결과 `pending`, 여전히 같은 작업임 | 상태 확인, 닫기 | 새 작업 시작, receipt가 있다고 표시 |
| `TS-40` | 성공, `R-72`, 유일 receipt `S-72`, 내 메모 | `D-SAVED` 진입, 닫기·다시 열기 | 두 번째 저장 관계나 receipt 생성 |
| `TS-90` | 인증 복구 필요, 결과 미확정, 같은 `K` 유지 | 인증 복구, 닫기 | 인증 뒤 임의 재전송, 성공·실패 추정 |

## 7. 경로 점검

| 경로 | 걸어 본 전이 | 결과 |
|---|---|---|
| 정상 성공 | `NAV-01 → TR-01 → TR-02 → TR-03 → TR-04 → TR-05 → TR-06 → TR-07 → TR-18` | 최초 timeout을 실패로 오판하지 않고, 두 번의 상태 확인 뒤 `S-72`로만 성공한다. `D-SAVED`에서 같은 `R-72`를 확인할 수 있다. |
| 결과 불명 복구 | `TR-03 → TR-04` | 허용된 복구가 저장 재전송이 아니라 같은 `K`의 상태 확인임을 확인했다. |
| 중복 저장 방지 | `TR-02 → TR-08` 또는 `TR-10` | 진행 중·확인 중에는 새 저장을 만들지 않고, 성공 뒤에도 두 번째 저장 관계나 receipt를 만들지 않는다. |
| 중복 상태 확인 방지 | `TR-04 → TR-09`, `TR-06 → TR-09` | 상태 확인이 이미 진행 중일 때 조회를 병렬로 늘리지 않는다. |
| 시작 전 닫기·복귀 | `TS-00의 TR-11 → TR-12` | 초안은 복원되지만 요청 키·receipt는 생기지 않는다. |
| 처리 중 닫기·복귀 | `TR-02 → TR-11 → TR-13 → TR-12` | 닫기가 서버 작업을 취소하지 않는다. 다시 열면 `TS-20`과 상태 확인 행동을 보여준다. |
| 상태 확인 중 닫기·성공 후 복귀 | `TR-06 → TR-11 → TR-15 → TR-12` | 닫힌 동안 성공해도 다시 열었을 때 `TS-40`과 `S-72`를 확인할 수 있다. |
| 성공 후 이탈·복귀 | `TR-07 → TR-11 → TR-12 → TR-18` | 성공이 초기화되지 않고, 내 보관함에서 같은 저장 관계를 확인할 수 있다. `D-SAVED`에서 상세로 돌아오는 규칙은 `OD-03`으로 남는다. |
| 목록 이탈·복귀 | `NAV-02 → NAV-03` | 검색어·태그·정렬·`R-72` 위치와 T-SAVE 상태를 함께 잃지 않는다. |
| 원문 이탈·복귀 | `NAV-04 → NAV-05` | 출처 링크를 목록 복귀로 오해하지 않고 현재 자료·입력을 보존한다. |
| 인증 복구 분기 | `TR-16 → TR-17` | 같은 키 재조회 API가 없어 더 진행할 수 없다. 새 요청을 만들지 않는 명시적 의존 상태로 끝난다. |

점검 결과 `TS-00`부터 `TS-40`까지의 확정 경로에는 고립 상태나 상충하는 guard가 없다. `TS-90`은 누락된 성공 경로가 아니라 `OD-02`에 의도적으로 연결한 미결 의존 상태다. 이 점검은 문서 내부 일관성 확인이며 실제 사용자 수용성 검증은 아니다.

## 8. 유지하는 미결 사항

| ID | 선행 미결 사항 | 이 흐름에 미치는 영향 | 결정 전 계약 |
|---|---|---|---|
| `OD-01` | 초대가 만료된 팀 자료를 읽을 수 있는가 | `D-LIB` 노출, 직접 URL, `D-ITEM` 진입 가능 여부가 달라짐 | 숨김과 접근 불가를 동일시하거나 새 권한 정책을 만들지 않는다. 진입이 허용된 뒤의 T-SAVE 흐름만 이 문서가 명세한다. |
| `OD-02` | 인증 복구 뒤 동일 `K`로 저장 작업을 재조회하는 서버 API | `TS-90`에서 원래 작업을 이어 확인할 수 있는지가 달라짐 | 인증 복구 뒤에도 새 저장 요청을 보내거나 결과를 성공·실패로 단정하지 않는다. API 결정 뒤 `TR-17`의 목적 상태를 보완해야 한다. |
| `OD-03` | 직접 URL·추천·`D-SAVED`에서 상세에 들어온 뒤 기본 복귀 목적지와 문맥 | `NAV-07` 이후의 뒤로가기 의미가 달라짐 | 선행 목록 문맥을 꾸며내지 않는다. 검색 결과에서 진입한 `NAV-01`의 확정 복귀만 적용한다. |
| `OD-04` | 최초 저장 요청 뒤 메모 편집 가능 여부와 편집분의 귀속 | 진행 중 초안과 최종 저장 메모가 달라질 수 있음 | `TS-10` 이후 편집 전이를 임의로 추가하지 않는다. 결정 시 요청 payload와 보존 초안의 관계를 함께 명시해야 한다. |

다음 선행 미정 세부도 그대로 남기며 T-SAVE 안에서 결정하지 않는다: 검색 대상 필드, 작성자 필터의 URL 표현, 필터 조합 방식, 목록별 콘텐츠 노출 분량, `D-HELP`의 세부 분류·정확한 탐색 위치. 이들은 확정된 검색 결과 진입과 저장 상태 전이를 작성하는 데는 차단 요소가 아니다.

## 9. 인계 상태

확정 경로는 상태·전이·보존 데이터·복구·이탈 규칙까지 후속 화면 명세가 추적할 수 있게 작성됐다. `OD-02`가 관련된 인증 복구 이후 경로와 `OD-04`의 진행 중 편집은 결정 전까지 구현 계약으로 간주하면 안 된다. 본 문서는 화면 배치나 코드의 승인안이 아니며, 사용자 수용 여부도 별도 검증 대상이다.
