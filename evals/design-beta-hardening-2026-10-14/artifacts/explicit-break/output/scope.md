# `break` 스킬의 역할 경계

## 역할

`break`는 한 번에 실제 컴포넌트 하나를 격리된 임시 페이지에 여러 도달 가능한 시나리오로 렌더링하고, 한 차례 눈으로 확인하여 실제로 보이는 파손만 기록하는 관찰용 스킬이다. 맥락 속 디자인의 좋고 나쁨을 평가하거나 대안을 탐색하지 않는다.

## 입력

- 대상은 하나의 컴포넌트여야 한다. 컴포넌트가 무엇을 입력받고, 무엇을 렌더링하며, 어디에 놓이는지가 확인되어야 한다.
- 컴포넌트의 props, 슬롯, 상태, 렌더링 데이터처럼 프로덕션에서 실제로 달라질 수 있는 표면이 시나리오 추론의 근거다.
- 시나리오 축은 콘텐츠 길이, 콘텐츠 형태, 항목 수, 컨테이너, 상태, 환경이다. 각 축은 `scenarios.md`의 적용 단서가 컴포넌트와 맞을 때만 유지한다. 컨테이너 축은 항상 적용하고, 나머지는 해당 능력이나 변이가 있을 때만 적용한다.
- 가변 텍스트의 상한을 기존 제약이나 콘텐츠에서 알 수 없으면 합리적인 가정을 명시해야 한다. 실제 상태나 데이터는 가져오지 않고 고정 fixture를 사용한다.

## 출력

정상적인 `break` 실행의 주 산출물은 앱 안의 임시 하네스 페이지다. 이 페이지는 실제 컴포넌트를 수정 없이 가져와 선택된 시나리오마다 한 번씩 세로로 렌더링하고, 각 인스턴스 위에 짧은 라벨을 둔다. 한 번의 브라우저 관찰에서 실제로 확인된 파손은 해당 시나리오 아래에도 한 줄로 표시한다.

함께 제공되는 텍스트 보고서는 깨진 시나리오를 먼저 나열하는 `시나리오 / 관찰 내용 / 소유 역할` 표다. 아무것도 깨지지 않았다면 “모두 견뎠다”는 결과와 페이지의 시나리오 목록 및 실행 위치만 보고한다. 예측이나 취향은 결과에 포함하지 않는다.

이번 역할 경계 확인의 산출물은 이 문서뿐이다. 임시 페이지, fixture, 시나리오 목록, 관찰 결과표는 만들지 않았다.

## 인접 역할

- `interface-review`, `better-interface`: 코드를 기준에 따라 검토하고 판단한다. `break`는 기준 검토나 판정을 하지 않는다.
- `variant`: 실제 페이지의 맥락에서 디자인 대안을 탐색한다. `break`는 의도적으로 컴포넌트를 격리하며 대안을 만들지 않는다.
- `state-machine`: 컴포넌트의 제품 상태를 하나씩 설계·검토한다. `break`는 이미 props로 도달 가능한 상태만 고정 fixture로 렌더링한다.
- `design-browser`: 완성된 하네스를 한 번 열어 시각 증거를 수집하는 보조 역할이다. 브라우저 설정이나 디버깅은 `break`의 범위가 아니다.
- `better-typography`, `better-layout`, `better-writing`, `better-accessibility`, `better-ui`, `better-colors`: 관찰된 파손을 각 도메인의 언어로 진단하고 수정하는 소유 역할이다. `break`는 소유자를 지정할 뿐, 그 규칙을 대신 적용하거나 수정하지 않는다.

## 중단 지점

정상 실행에서는 하네스를 한 번 로드해 모든 시나리오를 훑고, 눈에 보인 파손을 페이지와 보고서에 기록한 뒤 즉시 멈춘다. 계측, 반복 브라우저 검사, 브라우저 디버깅, 디자인 판정, 개선안 제시와 수정은 하지 않는다. 하네스 페이지는 보고서의 일부이므로 사용자가 삭제를 요청할 때까지 남긴다. 수정 요청이 별도로 오면 해당 소유 스킬의 규칙으로 수정한 뒤 실패 시나리오만 다시 렌더링해 확인한다.

이번 요청에서는 이보다 앞에서 멈췄다. 컴포넌트 선택, 소스 저장소 열람, 시나리오 추론, 하네스 구현, 서버 실행, `http://127.0.0.1:48924/runs/explicit-break/` 접속, 브라우저 관찰을 모두 수행하지 않았다. 따라서 실제 컴포넌트나 파손 여부에 관한 검증 결과는 없다.
