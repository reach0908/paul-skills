# `build-design` 역할 경계

## 이번 실행의 결론

`build-design`은 **승인된 디자인을 기존 프로젝트의 토큰과 컴포넌트로 구현하고, 구현 결과를 원본과 비교해 차이를 보고하는 역할**이다. 디자인 방향을 새로 탐색하거나, 완성된 인터페이스를 종합 평가하거나, 접근성·색상·문구 같은 전문 영역의 규칙을 새로 정하는 역할은 아니다.

이번 과제는 역할 경계 확인만 요구한다. 따라서 아래에 통상적인 입출력과 경계를 설명하되, 가상의 디자인 구현·프로젝트 매핑·브라우저 비교는 실행하지 않았다.

## 입력

통상적인 `build-design` 작업에는 다음 입력이 필요하다.

- 승인된 디자인 원본: 브라우저 프로토타입, Markdown 화면 명세, Figma 프레임, 스크린샷 또는 내보낸 이미지
- 구현 범위: 대상 화면·프레임, 리비전, 경로, 상태, 뷰포트 너비와 이미 결정된 사항
- 기존 프로젝트 자산: 디자인 토큰, 컴포넌트 라이브러리, 현재 데이터 연결과 필수 동작
- 비교 기준: 간격, 크기, 반경, 색상, 타이포그래피, 컴포넌트 값과 상태별 기대 결과

입력의 근거 수준도 구분한다. 명세에 적힌 값, 브라우저 계산값, 이미지에서 추정한 값은 서로 같은 확실도로 취급하지 않는다. 스크린샷만 있으면 크기는 캡처 비율에 따른 추정치이며, Figma 값이라고 주장하려면 Figma 디자인 컨텍스트에서 읽은 근거가 필요하다.

이번 역할 확인에 실제로 제공·열람한 과제 입력은 `TASK.md`, `PROMPT.md`, 그리고 로컬 `build-design/SKILL.md`뿐이다. 구현할 승인 디자인이나 프로젝트 자산은 입력으로 사용하지 않았다.

## 출력

통상적인 출력은 다음으로 구성된다.

- 합의된 화면·반응형 동작·상태를 기존 토큰과 컴포넌트에 맞춰 구현한 결과
- 지정된 너비와 상태에서 원본과 구현을 비교한 근거
- 요소별 `디자인 / 구현 / 상태` 비교표
- 필요한 경우 `연결되지 않음`, `누락 상태`, `도메인 충돌`, `편차` 보고
- 실행 위치와 실제로 비교한 뷰포트 너비

새 토큰이나 컴포넌트 변형, 임의의 원시 값을 추가해 숫자를 억지로 맞추는 것은 기본 출력 범위가 아니다. 기존 토큰으로의 반올림이 눈에 띄는 차이를 만들면 승인 없이 결정하지 않는다. 백엔드가 없으면 UI를 props 기반으로 만들 수 있지만, 반드시 연결되지 않은 항목으로 보고한다.

이번 과제의 유일한 산출물은 이 역할 경계 문서다. 코드, 화면 명세, Figma 프레임, 디자인 이미지, 브라우저 캡처는 산출하지 않았다.

## 인접 역할

| 영역 | 담당 역할 | `build-design`과의 경계 |
| --- | --- | --- |
| 브라우저 근거 수집·렌더링 확인 | `design-browser` | `build-design`이 비교에 필요한 관찰 목적과 기대 결과를 넘기고, 브라우저 증거 수집 절차는 이 역할을 따른다. |
| 대비 요구, 포커스, 시맨틱, 키보드 접근성 | `better-accessibility` | 시각적 충실도와 충돌하면 접근 가능한 동작을 보존하고 편차로 보고한다. |
| 색상 팔레트와 대비 측정 | `better-colors` | 색상 체계와 측정 기준을 소유한다. |
| 글꼴·타입 스케일·텍스트 렌더링 | `better-typography` | 타이포그래피 판단을 소유한다. |
| 간격·구조·반응형 배치 | `better-layout` | 레이아웃 체계 판단을 소유한다. |
| 라벨·오류·빈 상태 등의 문구 | `better-writing` | 제품 문구 판단을 소유한다. |
| 표면·아이콘·모션의 세부 완성도 | `better-ui` | UI 디테일 판단을 소유한다. |
| 완성 결과의 종합 리뷰 | `interface-review` | 구현 완료 후 평가하는 다음 단계이며 `build-design` 자체의 구현 역할과 구분된다. |
| 대안 탐색 | `variant` | 승인된 디자인을 구현하는 대신 새로운 방향을 탐색하는 역할이다. |
| 컴포넌트 스트레스 테스트 | `break` | 구현 대상 컴포넌트의 극단 조건을 시험하는 별도 역할이다. |

`interface-review`, `variant`, `break`는 이 스킬 문서가 인접 역할로 명시한 이름이다. 이번 실행에서는 호출하거나 가용성을 확인하지 않았다.

## 중단 지점

통상적인 `build-design` 작업은 다음 경계에서 멈추거나 사용자 결정을 요청한다.

- 승인된 디자인 원본이나 대상 리비전·화면·상태·너비가 정해지지 않아 구현 기준을 확정할 수 없을 때
- Figma가 입력인데 도구가 없거나 인증되지 않아 원본 값을 읽을 수 없을 때: 기억이나 추측으로 구현하지 않는다.
- 기존 토큰으로 반올림하면 간격·크기가 2px보다 크게 달라지거나 색상이 다른 단계로 이동해 눈에 띄는 차이가 생길 때
- 디자인 충실도가 접근성 또는 기존 필수 동작을 훼손할 때: 사용 가능한 최소 대안을 유지하고, 담당 영역과 승인 상태를 편차로 남긴다.
- 필요한 도메인 규칙이나 제품 결정이 없을 때: `build-design`이 새 규칙을 발명하지 않는다.

정상적인 완료 지점은 범위 안의 차이가 모두 수정되었거나, 합의된 반올림이 되었거나, 편차·질문으로 명시된 때다. 그 뒤에는 구현 위치와 실제 비교한 너비를 보고하고 멈춘다. 주변 문구 수정, 아이콘 교체, 관련 없는 정리, 새 제품 흐름 발명으로 범위를 넓히지 않는다.

이번 실행의 중단 지점은 더 이르다. 이 문서로 역할 경계를 설명한 시점에서 종료하며, 시뮬레이션된 디자인 과제는 시작하지 않는다.

## 확인 한계

- 소스 저장소, 다른 실행 작업공간, 평가 보고서, 과거 결과, 전역 메모리는 읽지 않았다.
- 프로젝트 토큰·컴포넌트·코드와 디자인 원본을 읽지 않았다.
- 브라우저를 실행하거나 제공된 URL 기준 경로를 열지 않았다.
- 실제 화면, 상태, 뷰포트 비교를 하지 않았으므로 구현 충실도나 픽셀 일치를 검증할 근거가 없다.
- 계정이나 라이브 API를 사용하지 않았고, 에이전트를 추가로 생성하지 않았다.
