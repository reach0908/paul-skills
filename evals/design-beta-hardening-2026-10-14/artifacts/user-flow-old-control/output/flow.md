# T-SAVE 상태·전이 명세

## 범위와 불변 조건

- 대상은 자료 상세의 메모 초안 저장 작업 `T-SAVE`뿐이다. 화면 코드, 상태 전시 페이지, 새 권한 정책은 범위 밖이다.
- 저장 성공은 서버가 성공을 확인하고 이 작업의 유일한 영수증 `S-72`를 반환했을 때만 확정한다.
- 최초 저장 요청의 타임아웃은 `timeout-unknown`이다. 서버가 요청을 처리했을 수도 있으므로 성공이나 실제 실패로 바꾸어 해석하지 않는다.
- `timeout-unknown`의 승인된 복구 동작은 같은 작업의 **상태 확인**이다. 새 저장 요청을 보내는 재시도가 아니다.
- 닫기는 서버의 진행 작업을 취소하지 않는다. 작성한 메모 초안은 닫기와 재진입을 거쳐 유지한다.
- 같은 요청에 대한 중복 저장 입력은 무시하고 새 저장 요청을 만들지 않는다.

## 상태 정의

| 상태 | 의미 | 성공 여부 | 영수증 |
|---|---|---|---|
| `draft` | 메모 초안을 작성 중이며 저장 요청은 아직 시작하지 않음 | 미확정 | 없음 |
| `pending` | 최초 저장 요청을 보냈고 서버 확인을 기다리는 중 | 미확정 | 없음 |
| `timeout-unknown` | 최초 요청이 타임아웃되어 서버 처리 여부를 알 수 없음 | 미확정. 실패도 성공도 아님 | 없음 |
| `check-pending` | 상태 확인 결과가 `pending`임. 원래 저장 작업은 계속 미확정 | 미확정 | 없음 |
| `succeeded` | 서버가 저장 성공을 확인함 | 성공 확정 | `S-72` 하나 |
| `failed` | 타임아웃과 달리, 실제 실패가 명시적으로 확인된 종결 상태 | 실패 확정 | 없음 |
| `auth-recovery-unresolved` | 인증 복구 뒤 같은 키로 작업을 재조회해야 하지만 이를 위한 서버 API 계약이 정해지지 않음 | 미확정 | 없음 |

`failed`에 이르는 구체적인 서버 응답, 실패 사유, 재시도 가능 여부와 재시도 방식은 자료에 결정되어 있지 않다. 따라서 이 명세는 실제 실패를 `timeout-unknown`과 구분만 하며 추가 정책을 확정하지 않는다.

## 상태 전이

| 번호 | 현재 상태 | 입력·관찰 | 다음 상태 | 동작과 제약 |
|---:|---|---|---|---|
| 1 | `draft` | 저장 입력 | `pending` | 메모 초안을 포함한 최초 저장 요청을 한 번 보낸다. 성공으로 표시하지 않는다. |
| 2 | `pending` | 같은 요청에 대한 중복 저장 입력 | `pending` | 입력을 무시한다. 새 저장 요청을 보내지 않는다. |
| 3 | `pending` | 최초 요청 타임아웃 | `timeout-unknown` | 서버 처리 여부가 불명이다. 실패 처리, 성공 처리, 새 저장 요청 재전송을 하지 않는다. 초안은 유지한다. |
| 4 | `timeout-unknown` | 상태 확인 실행 | `timeout-unknown` | 기존 작업의 상태만 조회한다. 저장 요청을 다시 보내지 않는다. |
| 5 | `timeout-unknown` | 첫 번째 상태 확인 결과 `pending` | `check-pending` | 작업을 미확정 상태로 유지한다. `S-72`를 만들거나 성공으로 표시하지 않는다. |
| 6 | `check-pending` | 두 번째 상태 확인 실행 | `check-pending` | 같은 작업의 상태만 다시 조회한다. 새 저장 요청이 아니다. |
| 7 | `check-pending` | 두 번째 상태 확인 결과 `succeeded` 및 영수증 수신 | `succeeded` | 성공을 확정하고 유일한 영수증 `S-72`를 결부한다. 추가 영수증을 만들지 않는다. |
| 8 | `pending` 또는 상태 확인 중인 미확정 상태 | 서버가 실제 실패를 명시적으로 확인 | `failed` | 타임아웃 추정이 아니라 명시적으로 확인된 경우에만 실패를 확정한다. 구체적인 실패 응답과 후속 복구 정책은 미정이다. |
| 9 | 저장이 미확정인 모든 상태 | 닫기 | 동일한 서버 작업 상태 유지 | 서버 작업을 취소하지 않는다. 메모 초안을 유지한다. 닫기는 저장 상태 전이가 아니다. |
| 10 | 닫힌 뒤 재진입 | 재진입 | 닫기 전 작업 상태로 복귀 | 유지한 초안을 복원한다. 서버 작업을 새 저장 요청으로 다시 시작하지 않는다. 단, 재진입 시 서버 상태를 동기화하는 구체 API·시점은 정해지지 않았다. |
| 11 | `succeeded` | 같은 요청에 대한 중복 입력 또는 중복 성공 신호 | `succeeded` | 새 저장이나 새 영수증을 만들지 않는다. `S-72` 하나만 유지한다. |
| 12 | 인증 복구가 필요한 미확정 상태 | 인증 복구 완료 후 같은 키로 작업 재조회 시도 | `auth-recovery-unresolved` | 동일 키 재조회용 서버 API가 미정이므로 호출 방식, 응답, 다음 전이를 확정하지 않는다. 이를 새 저장 요청으로 대체하지 않는다. |

## 핵심 흐름

`draft` → 저장 → `pending` → 타임아웃 → `timeout-unknown` → 상태 확인 1회(`pending`) → `check-pending` → 상태 확인 2회(`succeeded`, `S-72`) → `succeeded`

이 흐름에서 두 상태 확인은 최초 저장을 재전송하지 않는다. `S-72`는 두 번째 확인에서 서버 성공이 확인될 때 한 번만 수용한다.

## 미결 사항

- 인증 복구 후 **동일 키**로 기존 작업을 재조회하는 서버 API의 엔드포인트, 요청·응답 계약, 오류 처리는 미정이다.
- 동일 요청과 중복 입력을 판별하는 키의 생성·보관 위치 및 클라이언트/서버의 구체 중복 제거 방식은 정해지지 않았다. 요구되는 동작은 중복 입력을 무시하고 새 저장 요청과 추가 영수증을 만들지 않는 것까지다.
- 실제 실패를 알리는 구체 서버 응답, 실패 뒤 재시도 허용 여부, 재시도 시 키 정책은 미정이다.
- 닫은 뒤 재진입할 때 서버 상태를 언제·어떤 API로 동기화할지는 미정이다. 확정된 것은 서버 작업을 취소하지 않고 초안을 유지한다는 점이다.
