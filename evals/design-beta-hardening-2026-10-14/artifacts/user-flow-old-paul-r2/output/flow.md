# T-SAVE 사용자 흐름 전이 계약

## 문서 상태와 근거

- 산출물 범위: 자료 상세에서 메모 초안을 저장하는 `T-SAVE`만 다룬다.
- 기준 결정본: `BRIEF.md` — `PB-72 revision 3`, SHA-256 `021b535c16b5ce03adee05783634b4de533053afddf3148caea1d216362b42f6`
- 작업 지시: `TASK.md`, SHA-256 `d024db01b2fce4ef44856a314d3625116c6ee135946e1abf0ee7cf75bff5eeaf`
- 적용 스킬: `.agents/skills/user-flow/SKILL.md`, SHA-256 `a8b1a4df0fa20cf6b01ba49a969b8b33cc5620926e0d67ef7663e53a8f51d828`
- 상태: 하류 화면 명세에 사용할 수 있는 흐름 계약. 사용자 수용성이나 실제 서버 동작 검증을 뜻하지 않는다.

## 작업 경계

### 고정된 사실

- 행위자: 팀의 읽기 목록에서 자료를 찾아 자신의 보관함에 저장하려는 사용자.
- 진입점: `D-ITEM`(`/items/:id`)의 자료 `R-72`, 제목 **작은 팀에서 실패 후 다시 시도하기**.
- 의도한 결과: 입력한 메모가 포함된 저장 요청의 서버 성공을 확인한다.
- 관찰 가능한 성공: 서버가 유일한 receipt `S-72`와 함께 `succeeded`를 확인한 때뿐이다. 요청 시작, 타임아웃, `pending`은 성공이 아니다.
- 고정 응답 순서: 첫 저장 요청은 `timeout-unknown`, 첫 상태 확인은 `pending`, 두 번째 상태 확인은 `succeeded`와 `S-72`이다.
- 승인된 불명 상태 복구는 같은 작업의 **상태 확인**이다. 새 저장 요청을 재전송하지 않는다.
- 닫기는 서버 작업을 취소하지 않으며 메모 초안을 유지한다. 같은 요청에 대한 중복 저장 입력은 무시한다.
- 기존 뒤로가기 문맥 `q='작은 팀'`, `tag='운영'`, `sort='newest'`, 목록 위치 `item R-72`를 유지한다.

### 포함하지 않는 것

- 화면 배치, 컴포넌트 설계, 화면 코드, 상태 전시용 페이지.
- `D-LIB`, `D-SAVED`, `D-HELP` 전체 흐름이나 전역 정보 구조의 변경.
- 계정 생성, 실제 인증 수행, 라이브 API 호출.
- 메모와 원문의 소유권 정책 재정의.
- 만료된 팀 초대의 열람 권한 결정.

`D-SAVED`와 `D-HELP`는 기존 목적지로 유지하지만 이 계약이 새 이동 동작을 만들지는 않는다. `D-LIB`는 기존 뒤로가기와 재진입 문맥에만 사용한다. 입력 자료는 “닫기” 뒤의 목적지를 정하지 않았으므로 이 계약도 임의의 경로를 배정하지 않는다.

## 선행 조건과 성공 조건

- 시작 선행 조건: 사용자가 현재 정책상 열 수 있는 `R-72`의 `D-ITEM`에 있고 `T-SAVE`를 사용할 수 있다.
- 권한 예외: 초대가 만료된 팀 자료를 읽을 수 있는지는 `OD-02`로 미결이다. 이 경우의 진입·차단 전이는 정하지 않는다.
- 시작 데이터: 메모 초안은 비어 있거나 입력 중일 수 있다. 아직 저장 요청이 없다면 요청 키와 receipt는 없다.
- 성공 조건: 작업 상태가 `OS-60`이고 receipt가 정확히 `S-72`이다.
- 실패 조건: 서버가 실패를 명시적으로 확정해 작업 상태가 `OS-70`이 된 경우다. 시간 초과나 무응답만으로는 실패 조건을 충족하지 않는다.

## 상태 모델

서버 작업 상태와 상세 화면의 표시 여부를 서로 다른 축으로 관리한다. 닫기와 재진입은 `VS-*`만 바꾸며 `OS-*` 서버 작업을 취소하거나 새로 만들지 않는다.

### 작업 상태

| ID | 이름 | 사용자가 알아야 할 의미 | 보유 데이터 |
|---|---|---|---|
| `OS-00` | 요청 전 | 초안을 편집할 수 있고 저장 요청은 아직 없다. | 초안, 목록 복귀 문맥. 요청 키·receipt 없음 |
| `OS-10` | 최초 저장 요청 중 | 저장 요청을 한 번 시작했으며 결과를 기다린다. 성공으로 표시하지 않는다. | 초안, 동일 요청 키, `checkCount=0` |
| `OS-20` | 결과 불명 타임아웃 | 응답 시간이 지났지만 서버 처리 여부는 모른다. 실패나 성공으로 단정하지 않는다. | 초안, 동일 요청 키, `checkCount=0`, `receipt 없음` |
| `OS-30` | 상태 확인 중 | 기존 키로 기존 작업의 상태를 조회 중이다. 새 저장 요청이 아니다. | 초안, 동일 요청 키, 현재 확인 차수 |
| `OS-40` | 서버 pending 확인 | 첫 상태 확인에서 기존 작업이 아직 진행 중임을 확인했다. | 초안, 동일 요청 키, `checkCount=1`, `receipt 없음` |
| `OS-60` | 저장 성공 확인 | 서버가 `succeeded`와 유일 receipt `S-72`를 확인했다. | 저장된 메모, 동일 요청 키, `checkCount=2`, `receipt=S-72` |
| `OS-70` | 실제 실패 확인 | 서버가 실패를 명시적으로 확정했다. `OS-20`과 다른 종결 결과다. | 초안, 동일 요청 키, 확인된 실패 사실, `receipt 없음` |
| `OS-80` | 인증 복구 의존성 | 상태 확인에 인증 복구가 필요하지만, 복구 뒤 동일 키로 재조회할 서버 API 계약이 없다. | 초안, 동일 요청 키, 직전 확인 차수, `receipt 없음` |

### 보기 상태

| ID | 의미 | 허용되는 변화 |
|---|---|---|
| `VS-OPEN` | `R-72`의 `D-ITEM`에서 T-SAVE 상태를 볼 수 있다. | 작업별 행동, 닫기/뒤로가기 |
| `VS-HIDDEN` | 사용자가 T-SAVE 보기를 닫아 작업 상태가 보이지 않는다. 닫기 뒤의 실제 목적지는 미정이다. | 같은 T-SAVE 보기 재진입. 서버 작업은 그대로 지속될 수 있음 |
| `VS-AWAY` | 기존 뒤로가기로 `D-ITEM`을 떠나 `D-LIB`에 있다. | 보존된 목록 위치의 `R-72` 재진입. 서버 작업은 그대로 지속될 수 있음 |

초기 조합은 `(OS-00, VS-OPEN)`이다. 작업 상태 하나와 보기 상태 하나가 항상 함께 존재한다.

### 전이 해석 규칙

- `TR-02`는 실패 전이가 아니다. `OS-20`에서 성공 표시, 실패 표시, receipt 생성은 모두 금지한다.
- `TR-03`과 `TR-05`는 동일 키를 조회한다. 저장 본문을 다시 보내는 전이가 아니다.
- `TR-07`은 제품이 받은 중복 사용자 입력을 무시한다는 계약이다. 제공 자료에 없는 서버 측 멱등성 구현까지 보장하는 뜻은 아니다.
- `TR-08`은 명시적인 서버 실패만 다룬다. 제공된 R-72 고정 응답 시퀀스에서는 발생하지 않지만, `timeout-unknown`과 실제 실패를 같은 상태로 표현하지 않기 위해 둔다.
- `TR-10`은 의도적으로 완결하지 않는다. 화면 설계가 서버 API와 키 재조회 규칙을 대신 결정해서는 안 된다.
- `TR-11`과 `TR-13`은 `OS-10`, `OS-30`에서 진행 중인 네트워크 작업도 취소하지 않는다. 뒤이어 오는 서버 사건은 보이지 않는 보기 상태의 같은 작업에 적용한다.

## 화면이 노출해야 할 정보와 행동

시각 구성은 정하지 않고, 상태를 이해하고 다음 행동을 고르는 데 필요한 내용만 지정한다.

| 상태 | 반드시 알릴 정보 | 제공할 T-SAVE 행동 |
|---|---|---|
| `OS-00` | 현재 메모 초안, 아직 저장되지 않았다는 사실 | 초안 편집, 저장 |
| `OS-10` | 저장 요청 진행 중, 완료 미확정 | 닫기/뒤로가기. 반복 저장 입력은 새 요청을 만들지 않음 |
| `OS-20` | 타임아웃, 서버 처리 여부 불명, 성공·실패 모두 미확정 | 상태 확인, 닫기/뒤로가기 |
| `OS-30` | 기존 작업 상태를 확인 중이며 새 저장이 아님 | 닫기/뒤로가기. 반복 저장 입력은 무시 |
| `OS-40` | 서버 상태가 `pending`, receipt 없음 | 다시 상태 확인, 닫기/뒤로가기 |
| `OS-60` | 저장 성공, receipt `S-72` | 닫기/뒤로가기. 추가 저장 정책은 이 계약 밖 |
| `OS-70` | 서버가 확인한 실제 실패, 초안 유지, receipt 없음 | 닫기/뒤로가기. 재시도는 `OD-03` 결정 전 제공 여부 미정 |
| `OS-80` | 인증 복구 필요와 동일 키 재조회 API 미정, 자동 성공 아님 | 닫기/뒤로가기. 복구 후 재조회는 `OD-01` 결정 필요 |

자료 상세의 `출처로 이동`과 `본문으로 건너뛰기`는 현재 자료 ID, 초안, 작업 상태, 동일 요청 키를 바꾸지 않는다. 원문 URL은 자료 목록 이동으로 해석하지 않는다.

## 데이터 보존 계약

| 데이터 | 생성 시점 | 닫기/재진입 | 타임아웃·pending·실패 | 성공 |
|---|---|---|---|---|
| 메모 초안 | `OS-00` 입력 시 | 유지 | 유지 | 저장된 메모로 유지 |
| 동일 요청 키 | 첫 `TR-01` 시 확보 | 유지 | 유지 | receipt와 함께 유지 |
| 상태 확인 차수 | 첫 확인에서 `1`, 두 번째 확인에서 `2` | 유지 | 유지 | `2` 유지 |
| receipt | 생성하지 않음 | 존재할 때만 유지 | 없음 | 유일 값 `S-72` |
| 목록 복귀 문맥 | T-SAVE 진입 전부터 존재 | `q='작은 팀'`, `tag='운영'`, `sort='newest'`, 위치 `R-72` 유지 | 영향 없음 | 영향 없음 |

`OS-00`에서 닫고 재진입할 때는 초안만 복원한다. 아직 존재하지 않는 요청 키나 receipt를 만들어 복원하지 않는다.

## 경로 점검

### P-01 고정 성공 경로 — 통과

1. `(OS-00, VS-OPEN)`에서 초안을 입력한다(`TR-15`).
2. 저장한다(`TR-01`) → `OS-10`.
3. 최초 요청이 타임아웃된다(`TR-02`) → `OS-20`; 성공/실패/receipt 없음.
4. 상태 확인을 선택한다(`TR-03`) → `OS-30`, 확인 차수 1.
5. 서버 `pending`을 받는다(`TR-04`) → `OS-40`.
6. 다시 상태 확인한다(`TR-05`) → `OS-30`, 확인 차수 2.
7. 서버 `succeeded`와 `S-72`를 받는다(`TR-06`) → `OS-60`.

결과: 성공은 마지막 서버 확인에서만 식별되고, 저장 재전송이나 중복 receipt가 없다.

### P-02 요청 전 닫기와 재진입 — 통과

`OS-00`에서 초안을 입력한 뒤 닫는다(`TR-11`) → `(OS-00, VS-HIDDEN)`. 같은 T-SAVE 보기에 재진입한다(`TR-12`) → `(OS-00, VS-OPEN)`. 초안은 남고 요청 키와 receipt는 여전히 없다. 닫기 뒤의 실제 목적지는 입력 자료에 없어 명세하지 않았다.

### P-03 타임아웃 뒤 닫기와 재진입 — 통과

`OS-20`에서 닫고(`TR-11`) 다시 연다(`TR-12`). `OS-20`, 초안, 동일 키가 복원되며 다음 행동은 상태 확인이다. 저장 재전송으로 바뀌지 않는다.

### P-04 확인 중 닫기 — 통과

첫 상태 확인 직후 `OS-30`에서 닫는다(`TR-11`). 닫힘은 서버 확인을 취소하지 않는다. 서버의 `pending` 사건이 `TR-04`로 `(OS-40, VS-HIDDEN)`을 만든다. 재진입(`TR-12`)하면 `pending`과 “다시 상태 확인” 행동을 볼 수 있다.

### P-05 성공 뒤 닫기와 재진입 — 통과

`OS-60`에서 닫고 재진입한다(`TR-11`, `TR-12`). 성공 상태와 `S-72`가 유지되어 사용자가 완료 여부를 다시 구분할 수 있다.

### P-06 중복 저장 입력 — 통과

완료 전 같은 작업에서 저장 입력이 반복되면 `TR-07`이 현재 상태와 동일 키를 유지하며 새 저장 호출을 만들지 않는다. 불명 상태의 회복 행동은 계속 상태 확인이다.

### P-07 실제 실패 — 부분 명세, 정책 의존

서버가 명시적 실패를 확인한 경우에만 `TR-08`로 `OS-70`에 간다. 초안과 동일 키는 유지되고 receipt는 없다. 타임아웃과 구별되는 것까지는 명세됐지만, 새 키 재시도인지 같은 키 재시도인지는 `OD-03`이 미정이므로 그 이후 경로는 확정하지 않았다.

### P-08 인증 복구 — 미결 의존성에서 정지

상태 확인에 인증 복구가 필요하면 `TR-09`로 `OS-80`에 간다. 인증 복구 이후 같은 키로 작업을 재조회하는 서버 API가 미정이어서 `TR-10`의 도착 상태를 확정할 수 없다. 화면이 새 저장 전송이나 성공을 대신 가정해서는 안 된다.

### P-09 뒤로가기 문맥 — 통과

어느 작업 상태에서든 기존 뒤로가기로 `D-LIB`에 돌아가면 `q='작은 팀'`, `tag='운영'`, `sort='newest'`, 위치 `R-72`를 유지한다(`TR-13`). 여기서 `R-72`를 다시 열면 같은 작업 상태로 복귀한다(`TR-14`).

점검 결과: 정의된 상태 중 고립 상태는 없다. `OS-80`의 미완결은 누락이 아니라 이름 붙인 서버 의존성이다. `OS-70` 이후 재시도는 정책 미결 때문에 의도적으로 제공 행동을 확정하지 않았다.

## 검증 한계

- 이 문서는 제공된 `TASK.md`와 `BRIEF.md`만으로 작성한 저자 워크스루다.
- 요청 조건에 따라 계정과 라이브 API를 사용하지 않았고, 화면 코드나 기존 구현을 열거나 브라우저로 실행하지 않았다.
- 따라서 실제 서버가 타임아웃 뒤 같은 작업을 보존하는지, 중복 입력을 막는지, `pending → succeeded/S-72`로 응답하는지는 검증하지 않았다.
- 인증 복구, 만료 초대 권한, 실제 실패 뒤 재시도는 명시된 미결 정책 때문에 끝까지 실행할 수 없다.
- 내부 전이 일관성 점검은 사용자 테스트나 사용자 수용을 대신하지 않는다.
