# `variant` 역할 경계

## 이번 실행의 범위

이번 실행은 `variant` 스킬의 역할을 설명하는 경계 확인이다. 실제 UI 변형안, 선택기, 프로토타입, 구현 코드, 브라우저 조작 또는 디자인 평가는 만들지 않는다.

실제로 제공된 입력은 다음 두 가지뿐이다.

- `TASK.md`: 스킬의 현재 역할과 종료 경계만 설명하라는 지시
- `.agents/skills/variant/SKILL.md`: `variant`의 책임, 인접 역할, 작업 방식과 종료 조건

UI 컴포넌트 브리프나 제품 맥락은 제공되지 않았다. 따라서 아래 내용은 특정 디자인에 대한 제안이 아니라 스킬 계약의 설명이다.

## 스킬이 통상 받는 입력

`variant`는 한 번에 **하나의 UI 조각**에 대한 비교 요청을 받는다. 입력에는 최소한 다음 정보가 필요하다.

- 무엇을 비교할지: 예를 들어 대시보드 전체가 아니라 하나의 지표 카드
- 어디에 표시되는지: 실제 페이지, 주변 UI, 배경과 대상 화면 폭
- 무엇을 해야 하는지: 사용자가 완료해야 하는 과업과 유지해야 할 상태
- 무엇을 기준으로 다르게 만들지: 구조, 밀도, 강조, 타이포그래피 또는 문체 중 하나의 주축
- 제품의 바탕: 컴포넌트·스타일·모션 체계, 색·간격·모서리·타입·이징 토큰, 제품의 밀도와 문체
- 현실적인 콘텐츠와 데이터 규모

요청이 여러 UI 조각을 포함하면 `variant`가 임의로 넓히지 않는다. 후보를 나열한 뒤 사람이 탐색할 한 조각을 선택해야 한다.

## 스킬이 통상 만드는 출력

`variant`의 기본 산출물은 같은 브리프에 대한 **의도적으로 다른 세 가지 후보**다. 요청받은 경우에만 다섯 가지로 늘린다.

- 먼저 하나의 주축을 정하고, 각 후보에 겹치지 않는 위치와 방향을 드러내는 이름을 붙인다.
- 후보는 색조만 바꾼 복제품이 아니라 같은 문제에 대한 서로 다른 답이어야 한다.
- 실제 페이지 맥락에서 한 번에 하나씩 전체 크기로 렌더링한다.
- URL 매개변수와 별도의 플로팅 선택기로 후보를 전환하며, 전환 중 작업 상태를 보존한다.
- 각 후보는 접근성, 키보드 도달성, 포커스 표시, 축소 화면·확대, 대비, 오류 복구 등 동일한 최소 품질선을 충족해야 한다. 이 품질선은 변형 축이나 교환 가능한 비용이 아니다.
- 마지막에는 각 후보의 축 위치, 적합한 상황과 비용을 표로 제시하고 판단을 사람에게 넘긴다.

이 스킬은 후보를 만들지만 순위를 매기거나 선호안을 표시하지 않는다.

## 인접 역할

| 역할 | 담당 범위 | `variant`와의 경계 |
| --- | --- | --- |
| `interface-review`, `better-interface` | 기존 UI의 종합 검토 | 기존 화면을 평가하는 일이며, 후보 비교를 만드는 `variant`의 역할이 아니다. `better-interface`의 중대한 품질 기준은 모든 후보가 지켜야 할 바닥선으로만 적용된다. |
| `break` | 한 컴포넌트의 스트레스 테스트 | 실패 조건과 극단 상황을 찾는 역할이며, 의도적으로 다른 디자인 후보를 만드는 역할이 아니다. |
| `state-machine` | 컴포넌트 상태와 전이 정리 | 상태 모델을 설계하는 역할이며, 하나의 시각·구조 축에서 후보를 비교하는 역할이 아니다. |
| `prototype` | 더 넓은 임시 UI 또는 로직 질문 탐색 | 한 컴포넌트 비교보다 넓은 문제를 다룬다. 명시적인 단일 컴포넌트 변형 요청은 `variant`가 맡는다. |
| `better-layout` | 구조와 밀도 | 해당 축의 전문 역할이다. `variant`는 선택된 한 축에서 후보 세트를 조직한다. |
| `better-colors` | 시각적 강조 | 강조 축의 전문 역할이며, 단순 색상 차이만으로 변형 세트를 만들 수는 없다. |
| `better-typography` | 타입 스케일·대비·행 길이 | 타입 축의 전문 역할이다. |
| `better-writing` | 라벨·어조·카피 분량 | 문체 축의 전문 역할이다. |
| `design-browser` | 렌더링·상호작용·콘솔·짧은 뷰포트의 브라우저 증거 수집 | 실제 변형 작업의 검증 단계에서 사용하지만, 이번 경계 설명에서는 브라우저를 조작하지 않는다. |

명시적으로 호출된 `variant`가 한 컴포넌트의 비교를 소유하더라도, 사용자가 인접 역할을 별도로 요청했다면 어느 역할을 추가로 사용할지는 사람이 정한다.

## 종료 지점

일반적인 탐색 단계에서 `variant`는 세 후보가 실제 맥락에서 작동하는지 확인하고, 중립적인 장단점과 확인한 화면 폭을 제시한 뒤 **사람의 선택을 기다리는 지점에서 멈춘다**. 선호 후보를 스스로 선언하거나, 선택 전에 프로덕션 구현으로 승격하지 않는다.

사람이 하나를 선택해 승격을 요청한 경우에만 선택안을 제품 관례에 맞게 구현하고 나머지 후보, 선택기, 조건부 import와 `__variant` 흔적을 제거한다. 다른 탐색 라운드를 요청하면 선택기를 유지한 채 새 축 위치를 다시 정의한다.

이번 실행의 종료 지점은 이 문서 작성이다. 다음 작업은 수행하지 않았다.

- 소스 저장소, 다른 시험 작업공간, 평가 보고서, 과거 결과 또는 전역 메모리 열람
- UI 브리프 추정, 변형 방향·이름·주축 제안
- 디자인·코드·선택기·페이지·프로토타입 제작
- 제공된 URL 베이스에서의 페이지 접속 또는 브라우저 검증
- 접근성, 대비, 반응형 동작, 콘솔 상태 또는 후보 간 동등성 평가
- 후보 순위 결정, 선호안 추천 또는 자체 채점

따라서 이 문서는 스킬의 계약과 경계만 설명하며, 실제 산출물의 품질이나 작동 여부를 입증하지 않는다.
