# T-SAVE 상태·전이 명세

## 범위와 판정 원칙

이 문서는 자료 상세의 메모 저장 작업 `T-SAVE`만 다룬다. 화면 구성, 새 권한 정책, API 경로·메서드·응답 형식은 범위 밖이다.

- `요청 키 K`: 한 번의 저장 작업을 식별하는 동일 키다. 키의 생성·보존 방식은 이 문서에서 정하지 않는다.
- 성공은 서버가 유일한 receipt `S-72`를 확인했을 때만 확정한다.
- 타임아웃은 결과를 모르는 상태이지 실패가 아니다.
- 타임아웃 뒤 허용된 복구 동작은 동일 키의 **상태 확인**뿐이다. 저장 요청을 다시 보내지 않는다.
- 서버가 실패를 명시적으로 확인한 경우만 실제 실패로 판정한다. 실패 사유, 재시도 가능 여부와 새 요청 생성 정책은 미정이다.
- 화면의 열림/닫힘과 서버 작업 상태는 별개다. 닫기는 서버 작업을 취소하지 않으며 메모 초안은 유지한다.

## 작업 상태 표

| 상태 ID | 의미 | 사용자에게 구분해 전달할 핵심 | 허용되는 다음 동작 |
|---|---|---|---|
| `DRAFT` | 메모 초안을 입력·수정 중이며 저장 요청은 아직 없다. | 저장 전 초안 | 저장 시작 |
| `SAVE_PENDING` | 요청 키 K의 저장 요청을 한 번 보냈고 서버 확인을 기다린다. | 저장 진행 중, 성공 아님 | 응답 대기, 닫기 |
| `TIMEOUT_UNKNOWN` | 최초 저장 요청이 타임아웃됐다. 서버가 처리했는지는 알 수 없다. | 결과 미확인. 성공·실패로 표시하지 않음 | 동일 키 상태 확인, 닫기 |
| `STATUS_PENDING` | 동일 키 상태 확인 결과가 `pending`이다. 저장 요청은 추가되지 않았다. | 서버에서 아직 처리 중, 성공 아님 | 동일 키 상태 다시 확인, 닫기 |
| `SUCCEEDED` | 동일 키 상태 확인에서 `succeeded`와 유일 receipt `S-72`가 확인됐다. | 저장 완료 (`S-72`) | 종료 상태. 같은 요청의 중복 입력 무시 |
| `FAILED` | 서버가 해당 작업의 실패를 명시적으로 확인했다. | 실제 저장 실패. 타임아웃과 다른 상태 | 후속 복구·재시도 정책은 미정 |
| `AUTH_RECOVERY_REQUIRED` | 상태 확인 과정에서 인증 복구가 필요하다. | 인증 복구 뒤 동일 키 재조회 방법이 아직 정해지지 않음 | 아래 열린 결정 전에는 전이 확정 불가 |

`CLOSED`는 작업 상태가 아니라 화면 상태다. `SAVE_PENDING`, `TIMEOUT_UNKNOWN`, `STATUS_PENDING`에서 닫더라도 서버 작업 상태와 요청 키 K는 그대로이며 초안도 유지한다. 재진입은 저장 요청을 새로 보내지 않고 유지된 초안을 보여준다. 재진입 뒤 동일 키 상태를 어떤 서버 API로 다시 조회할지는 인증이 유효한 범위에서만 상태 확인 원칙을 적용하며, 인증 복구가 끼는 경우에는 아래 미결 사항을 따른다.

## 전이 표

| # | 시작 상태 | 사건 / 사용자 입력 | 서버 관찰 | 도착 상태 | 필수 처리 |
|---:|---|---|---|---|---|
| 1 | `DRAFT` | 저장 선택 | 요청 키 K로 저장 요청 1회 전송 | `SAVE_PENDING` | pending 표시. 초안 유지 |
| 2 | `SAVE_PENDING` | 첫 요청 타임아웃 | 처리 여부 알 수 없음 | `TIMEOUT_UNKNOWN` | 성공/실패로 단정하지 않음. 자동 또는 수동 저장 재전송 금지 |
| 3 | `TIMEOUT_UNKNOWN` | 상태 확인 | 동일 키 K 조회 결과 `pending` | `STATUS_PENDING` | 새 저장 요청 없이 처리 중으로 표시 |
| 4 | `STATUS_PENDING` | 두 번째 상태 확인 | 동일 키 K 조회 결과 `succeeded`, receipt `S-72` | `SUCCEEDED` | 이 확인에서만 저장 완료 표시. `S-72`를 해당 작업의 유일 receipt로 취급 |
| 5 | `SAVE_PENDING` / `TIMEOUT_UNKNOWN` / `STATUS_PENDING` | 서버가 실패를 명시적으로 확인 | 명시적 실패 | `FAILED` | 실제 실패로 표시. timeout-unknown 문구와 혼용하지 않음 |
| 6 | `SAVE_PENDING` / `TIMEOUT_UNKNOWN` / `STATUS_PENDING` / `SUCCEEDED` | 같은 요청의 저장 입력이 다시 들어옴 | 추가 저장 요청 없음 | 상태 유지 | 중복 입력 무시. 요청 키 K와 서버 작업은 하나로 유지 |
| 7 | `SAVE_PENDING` / `TIMEOUT_UNKNOWN` / `STATUS_PENDING` | 닫기 | 서버 작업에 취소 요청 없음 | 작업 상태 유지 + 화면 `CLOSED` | 초안과 동일 작업 문맥 유지 |
| 8 | 화면 `CLOSED` | 자료 상세 재진입 | 새 저장 요청 없음 | 보존된 작업 상태 + 화면 열림 | 유지된 초안을 복원. 재진입 자체로 저장 재전송 금지 |
| 9 | `TIMEOUT_UNKNOWN` / `STATUS_PENDING` | 상태 확인에 인증 복구 필요 | 동일 키 재조회 API 미정 | `AUTH_RECOVERY_REQUIRED` | 인증 복구 뒤 조회를 성공한 것으로 가정하지 않음 |
| 10 | `AUTH_RECOVERY_REQUIRED` | 인증 복구 완료 | **미정** | **미정** | 동일 키 K로 작업을 재조회할 서버 API가 결정될 때까지 전이, 자동화, 성공/실패 판정을 확정하지 않음 |

## 중복·닫기 불변 조건

| 조건 | 반드시 지킬 결과 |
|---|---|
| 같은 요청의 저장 입력이 여러 번 발생 | 최초 저장 요청 외 추가 저장 요청을 만들지 않는다. |
| 타임아웃 뒤 상태 확인 | 저장 재전송이 아니라 동일 키 K의 조회다. |
| 첫 상태 확인이 `pending` | 성공도 실패도 아니다. `STATUS_PENDING`을 유지한다. |
| 두 번째 상태 확인이 `succeeded` + `S-72` | `SUCCEEDED`로 확정한다. 별도 receipt를 만들지 않는다. |
| 처리 중 화면 닫기 | 서버 취소로 해석하지 않는다. 초안과 작업 문맥을 유지한다. |
| 재진입 | 재진입만으로 저장 요청을 보내지 않는다. |

## 열린 결정

인증 복구 후 동일 요청 키 K로 작업을 재조회하는 서버 API가 아직 결정되지 않았다. 따라서 endpoint, 인증 갱신과 조회의 순서, 자동/수동 재조회 여부, 오류 응답, 조회 불가 시 후속 동작은 이 명세에서 확정하지 않는다.
