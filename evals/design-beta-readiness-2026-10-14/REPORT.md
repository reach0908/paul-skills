# 남은 디자인 베타 8개 검증과 승격 보완안

2026-10-14. 평가 대상은 `skills/in-progress/`의 8개이며, 이미 정식 배포한 디자인 9개와 구분한다. 이번 작업에서는 스킬 내용, 출처 등록, 플러그인, 전역 설치를 바꾸지 않았다.

**8개 일괄 승격은 보류한다.** 새 과제 기준으로 6개는 요구한 기술적 결과를 충족했다. `break`는 원본보다 약한 결함 탐지 사례, `user-flow`는 문서 내부 불일치가 남았다. 기술적 통과 6개도 실제 호출 경계, 단계 간 전달, 사용자 수용과 승격 승인을 마쳤다는 뜻은 아니다.

## 새 평가 방법

- 역할마다 새 과제 하나를 두 조건에서 실행했다. 총 8쌍, 16개 독립 Codex CLI 문맥이다. 모델은 `gpt-5.6-sol`, reasoning effort는 `xhigh`로 동일하다.
- 실행 전 [프로토콜](PROTOCOL.md), 원본·후보·의존성 파일, 과제 입력을 동결했다. 8쌍 모두 과제 입력 해시가 같았다. 실행자에게 평가 기준, 다른 조건의 결과, 이전 실패를 제공하지 않았다.
- 가상 한국어 자료함 PB-72를 사용했다. IA와 flow는 문서 계약, wireframe은 결과 불명 저장의 복구, state-machine과 break는 실제 DOM 컴포넌트, explain은 두 페이지의 시스템 분석, variant는 밀도 비교, build는 승인된 로컬 카드 시안이 대상이다.
- 브라우저 과제는 양쪽 모두 작업 전용 Chrome 세션을 같은 방식으로 준비했고, 실제 관찰은 Playwright CLI로 수행했다. 평가자도 최종 산출물을 별도 세션에서 재실행했다.
- 과거 2026-10-12 반복 대표 과제를 보완하는 새 입력이지, 모든 입력·모델에 대한 통계적 비열등성 검정은 아니다. 독립 실행 사이에서 조건을 수정하지 않았다. 실행 안에서 산출물을 고치고 재검증하는 것은 스킬의 작업 과정으로 기록했다.
- 기획 전용 과제의 공통 안내에 조건부 브라우저 준비 문구가 포함되어 Paul 쪽에서 불필요한 브라우저 시도가 발생했다. 이를 기능 실패나 효율 비교에 사용하지 않는다. 다음 준비 도구에서는 역할별 안내를 분리해야 한다.
- 모든 호출은 명시적으로 요청했다. 이 결과로 자연어 자동 발견을 통과했다고 주장하지 않는다. 대조군의 명령 기록에 디자인 스킬 본문 읽기는 없었으나, 전역의 다른 스킬 메타데이터가 전혀 없는 보안 격리 환경은 아니었다.

## 확인된 보완 항목

### 1. break: 스트레스 데이터의 결함 탐지력이 원본보다 약했던 사례

두 조건 모두 같은 컴포넌트와 CSS를 보존하고 15개 시나리오를 생성했다. 원본은 빈 라벨, 공백 없는 긴 제목, 320px 컨테이너에서 깨짐을 보고했다. Paul은 빈 라벨 하나를 보고했다.

독립 재측정에서 원본의 긴 제목 버튼은 카드 오른쪽보다 약 209.20px, 좁은 카드 제목은 약 102.64px 넘쳤다. Paul의 긴 문자열은 같은 928px 카드 안에 들어갔고, 320px 카드에는 짧은 보통 제목을 넣어 넘침이 발생하지 않았다. 따라서 **눈앞의 넘침을 못 보고 없다고 쓴 오류는 아니다.** 생성한 입력이 같은 CSS 결함을 드러내지 못한 탐지력 차이다. 단일 실행으로 원인이 스킬의 특정 문장이라고 단정할 수도 없다.

사용자의 원본 이상 기준에서는 이 비교를 합격으로 넘길 수 없다. 원본이 드러낸 유효한 결함을 후보의 시나리오가 드러내지 못했다. 한 번 관찰이라는 역할은 유지하면서, 관찰 전에 현실적인 최장 텍스트와 좁은 컨테이너의 조합을 준비하도록 보완하는 것이 우선이다. 제품 CSS를 바꾸거나 가상의 결함을 보고하게 만드는 수정은 피한다.

종료 기준: 이번 사례와 별도의 새 컴포넌트에서 원본이 찾아낸 유효한 깨짐을 빠뜨리지 않고, 무결함 대조 화면에는 허위 지적을 만들지 않아야 한다. 단일 로드·단일 관찰·제품 미수정 조건도 함께 유지한다. [측정 결과](evidence/break-geometry-replay.txt), [원본 보고서](artifacts/break-original/output/report.md), [Paul 보고서](artifacts/break-paul/output/report.md).

### 2. user-flow: 상태 표와 전이 표의 닫기 범위 불일치

Paul 상태 표는 `ST-READY`와 `ST-SUCCEEDED`에서 닫기를 허용하지만 권위 있는 `TR-10` 닫기와 `TR-11` 복원 목록은 두 상태를 빠뜨렸다. 핵심 복구 경로와 `S-72` 성공은 명세됐으며, 실제 실행에서 데이터가 사라졌다는 증거는 아니다. 대조군도 모든 상태의 닫기를 명시적으로 검증하지 않아 대조군 대비 열위로 판정하지 않는다. 문서 내부 일관성 결함으로 분류한다.

종료 기준: 열림/닫힘을 작업 상태와 독립된 축으로 정의하거나 누락 전이를 추가한다. `READY → 닫기 → 복원`에는 아직 없는 요청 키를 요구하지 않고, `SUCCEEDED → 닫기 → 복원`에는 `S-72`를 유지하며 재전송하지 않아야 한다. 상태·행동·전이 표를 같은 경로로 다시 걷는다. [Paul 계약](artifacts/user-flow-paul/output/flow.md), [대조군 계약](artifacts/user-flow-control/output/flow.md).

### 3. variant: 최종 통과와 실행 중 실패를 함께 보존

Paul 실행은 모바일 메모 초점이 고정 picker와 겹치는 현상, 비교 캡처에서의 가림, picker 폭 축소, `scrollIntoView()`로 인한 문서 스크롤 이동을 찾아 수정했다. 같은 스킬 실행 안에서 산출물을 보완한 것이며 스킬 파일을 바꾸거나 실패를 지우고 새 독립 실행으로 세지 않았다. 최종 결과는 원본과 동일하게 검색·메모·비운 값·pending·완료 상태를 보존했고, 평가자도 2폭 × 3안에서 12개 컨트롤의 Tab 도달과 가림·넘침을 확인했다.

원본 compact의 320×450에서는 메모 초점 시 입력란 하단이 viewport 아래에 일부 남았다. 컨트롤은 도달 가능했으므로 완전한 접근 불가로 과장하지 않는다. Paul에는 같은 제한이 없었다. 이 한 관찰만으로 보편적인 우위를 주장하지 않는다. [상태 보존 재검증](evidence/variant-replay.txt), [새 문서의 키보드 재검증](evidence/variant-keyboard-replay.txt), [안정 후 compact 확인](evidence/variant-compact-focus-replay.txt), [Paul 보고서](artifacts/variant-paul/output/report.md).

이번 실패는 최종 후보의 미해결 회귀로 세지 않는다. 다만 고정 picker의 문서 위치·컨트롤 가림·현재 값을 포함한 검사를 재사용 가능하게 만들면 같은 실패를 반복해서 수동 복구하는 비용을 줄일 수 있다.

### 4. 나머지 역할의 기술 증거

- **IA:** 4개 목적지, 태그/작성자 필터, 동일 R-72의 여러 진입 경로, 검색·태그·정렬·항목 복귀 문맥, 모바일 도달성, 만료 초대와 메모 소유권의 미정 정책을 양쪽 문서에서 확인했다. 사용자 조사로 포장하지 않았다. [Paul 지도](artifacts/information-architecture-paul/output/map.md), [대조군 지도](artifacts/information-architecture-control/output/map.md).
- **wireframe:** 평가자가 각 조건의 두 폭에서 실제 키 입력과 Enter/Space를 사용해 결과 불명 → 상태 확인 pending → S-72, 중복 저장 비활성화, 닫기·reload·복원, 내부 출처 이동, 목록 왕복을 확인했다. 4개 조합 모두 가로 넘침과 해당 재실행의 page error가 없었다. Paul의 목록 이동 중 UI 업데이트 guard는 최종 산출물에 있지만 수정 전 런타임 실패를 직접 재현한 증거는 없어 실패 건수에 넣지 않는다. [재검증](evidence/wire-replay-result.txt), [화면 명세](artifacts/wireframe-paul/output/screens.md).
- **state-machine:** 원본 9개, Paul 10개 상태는 모두 실제 `renderQueueCard`를 import한다. Paul의 추가 상태는 실제 props의 refreshing+locked 조합이다. loading 유지, locked의 disabled, URL/reload/resize, 숫자·화살표·H를 확인했다. 입력·수정키·preventDefault 검사는 제품을 바꾸지 않고 일회성 DOM 입력과 이벤트 listener를 넣은 평가자 probe임을 구분한다. [재검증](evidence/state-break-replay.txt).
- **explain-interface:** 각 실행자가 8개 페이지/폭/테마 조합을 관찰했다. 평가자도 실제 24/16px 간격, 24/20px 제목, 2열/1열, 밝은/어두운 색과 교차 출처 `SecurityError`를 확인했다. WAAPI 1200ms의 25% 키프레임과 감소 모션의 animation 미생성은 실행자의 브라우저 명령 증거 및 설명과 fixture 소스가 일치했다. [재검증](evidence/explain-replay.txt), [설명](artifacts/explain-interface-paul/output/explanation.md).
- **build-design:** 4개 참조/결과 PNG 쌍의 SHA-256이 모두 같다. 평가자의 요소 사각형·패딩·색·반경·타입·열 측정도 일치했다. 각 조건의 두 폭에서 pending/disabled, 완료, 오류, 빈 결과, 비우기를 키보드로 확인했다. `app.js`와 기존 마크업은 그대로다. 공동 brief의 더 복잡한 저장 복구와 제공 앱의 1초 성공 동작은 서로 다르지만, 이 과제는 기존 동작 보존과 CSS 수정만 허용했다. 그 차이를 밝히고 app.js를 보존한 것이 올바른 범위 준수다. [이미지 해시](evidence/build-image-comparison.json), [재검증](evidence/build-replay.txt), [Paul 보고서](artifacts/build-design-paul/output/report.md).

## 승격 전에 남는 공통 조건

1. **호출 경계:** IA, user-flow, wireframe, build-design은 자동 또는 명시 호출 대상이다. state-machine, break, explain-interface, variant는 명시 호출 전용이다. 새 실제 호스트 세션에서 4개 자동 발견, 8개 명시 도달, 이웃 요청에서 명시 전용 역할의 무단 실행 방지를 확인한다. user-flow와 구현 상태 작업대, variant와 prototype, build-design과 새 디자인 탐색을 구분해야 한다.
2. **현재 산출물 간 전달:** 최신 IA → flow → wireframe → build를 한 실제 작업에서 연결해 ID, 미결 정책, 초안, pending, 복귀 문맥이 유지되는지 확인한다. 이번 역할별 공통 brief는 실제로 앞 단계가 만든 결과를 다음 단계가 받은 연결 시험을 대신하지 않는다.
3. **사용자 수용:** 특히 variant의 비교 방식과 build의 시안 충실도가 실제 업무에 충분한지 사용자가 확인해야 한다. 기하·동작 통과는 외관 선택이나 사용자의 수용을 대체하지 않는다. 모든 베타의 정식 승격에는 별도 명시 승인이 필요하다.
4. **승인 후 패키징:** 그때 design bucket, README, docs, ask-matt, manifests, provenance, Changeset을 함께 변경하고 검사·새 설치를 검증한다. 현재 베타가 정식 플러그인에 포함되지 않은 것은 의도된 상태다.

Figma는 사용자 범위 밖이므로 로컬 경로 승격의 필수 조건에 넣지 않는다. 실제 서버, 인증 복구, 네이티브 UI, 전체 보조기기·브라우저 조합, 사용자 tree test를 이번 결과로 인증하지 않는다.

로컬 서버가 실행 중일 때 다음 비교 결과를 열 수 있다. 가상 카드 평가용 산출물이며 실제 제품의 디자인 선택을 대신하지 않는다.

## 권장 실행 순서와 종료 조건

1. **P1: break와 user-flow만 최소 보완한다.** 관찰 횟수를 늘리는 범용 QA 역할로 break를 바꾸지 않는다. 실패 사례를 유지하고 역할당 별도 새 과제 한 쌍에서 확인한다. 원본의 유효한 발견 누락 0, 무결함 화면 허위 지적 0, 상태/전이 모순 0이 종료 조건이다.
2. **P2: 호출과 전달을 묶어 검증한다.** 격리된 실제 호스트의 긍정·부정 호출, 4개 자동/4개 명시 정책, IA → flow → wireframe → build 전달 한 건을 확인한다. ID·결정·미결 정책·사용자 작업을 재해석하거나 잃지 않아야 한다.
3. **P2: 사용자 수용 후 준비된 역할만 승격한다.** variant와 build는 같은 화면·폭·상태의 결과를 보여주고 비교 품질과 시안 충실도를 확인받는다. 8개 동시 승격을 목표로 결함과 승인을 합쳐 처리하지 않는다. 이미 통과한 역할은 미달 역할과 별도로 판단할 수 있다.
4. **P3: 검증 도구를 정리한다.** 원본의 임시 Git clone 대신 고정 manifest로 확인한 source bundle을 준비할 수 있게 한다. 역할별 브라우저 안내, 실패/수정 기록, 캡처 상태 고정, 빈 선택자 개수 단언, 실제 Tab 대상 목록을 재사용한다. 확대·RTL·실제 보조기기·서버 동시성 등 확장은 해당 제품 입력이 생길 때 추가한다.

## 증거 보존과 한계

16개 실행이 완료됐고 종료 코드는 모두 0이다. 이것은 동작 통과 수가 아니다. 완료 코드와 별도로 위 결과를 판정했다. 과제·스킬 입력 무결성, 변경 파일, 명령 실패, 출력 해시는 [run-integrity.json](run-integrity.json)에 보존했다. 역할별 원문 산출물과 실행 명령은 `artifacts/<run>/`에 있다. 제품 미수정 역할의 입력 파일은 그대로이며, build는 허용된 CSS만, variant는 허용된 앱 파일만 변경했다. wireframe은 허용된 로컬 앱을 생성했다.

독립 조건의 스킬 본문과 의존성 파일은 실행 전후 동일했다. 원문 산출물·참조·평가자 관찰을 포함한 PNG 85개의 크기와 해시는 [캡처 목록](evidence/captures.json)에 있다. 이 수는 테스트 케이스 수가 아니다. 평가용 인증 symlink는 실행 종료 후 제거했으며, 인증 파일이나 계정 데이터는 보고서 디렉터리에 포함하지 않았다. 결과 페이지는 로컬 서버에 유지하고 사용한 작업 전용 브라우저 세션은 닫았다.

평가자 도구 오류도 남겼다. 첫 break 계측은 잘못된 선택자 때문에 빈 결과여서 판정에 사용하지 않았고, 실제 `.card` 15개를 단언한 후 다시 측정했다. wireframe의 확인 대화상자는 CLI가 반환값보다 먼저 제어를 넘겨 결과를 별도 회수했다. variant의 첫 키보드 재실행은 이전 문서 초점의 영향이 있어 about:blank를 거친 새 문서에서 동일 목표를 재확인했다. 해당 기록을 지우거나 검사 기준을 완화하지 않았다.

`npm run check`는 버전·스킬 정합성과 38개 테스트를 통과했다. 이 검사는 AI 결과의 원본 동등성을 증명하는 검사가 아니다. 스킬 행동 변경이 없어 이번 평가 문서에는 Changeset이나 승격용 manifest 변경을 추가하지 않았다.

시간·비용의 우열은 판정하지 않는다. 요청한 5분은 가이드였고 일부 실행은 내부 수정·재검증으로 초과했다. 실행별 elapsed와 사용량은 영수증에 있지만 동시 실행·브라우저 준비·재시도 차이를 통제한 효율 실험이 아니었다.
